# 产品转向决议 · AI 个人第二大脑（2026-10-18）

> 📌 **证据等级**：本文的「现状事实」一节每条都可用文末的取证命令复跑；「决策」一节是项目所有者在本轮谈话中逐项拍板的结果，**未动一行代码**。
> 本文是**决策记录**（decision record），不替代 ADR——正式架构决策落 `docs/adr/0003-*.md`，数据模型与插件规范另立文档（见 §5）。

## 0. 一页结论

| | 结论 |
|---|---|
| **产品定位** | 从「刷卡学习 App」转向 **AI 个人第二大脑 / 知识中枢**：极速收集 → AI 结构化整理 → 检索与温故 |
| **形态** | 桌面端优先（Windows / macOS），三栏工作台 + 全局快捷键呼出的闪念胶囊；Android / iOS / Web 后续辐射 |
| **AI 地位** | **本地基础能力全部离线可用**，AI 只做增值（语义检索、自动归档、自动出卡、简报、跨内容问答） |
| **底座** | 以 `apps/workbench`（Tauri 2 + React 19 + TS）为起点重构；存储从单文件 JSON 升级为嵌入式 SQLite |
| **边界** | 先本地离线，不做云同步但**数据模型预留**；不引入 OpenViking 等重外部服务（理由见 §3.4） |
| **交付路线** | M1 地基（存储/入库/搜索/三栏壳）→ M2 多源收集 + AI 提炼 → M3 第二大脑问答 + 简报 → M4 温故复习 + 打包分发 |

**一句话**：先把「东西进得来、找得到、不丢」做扎实，再把 AI 叠上去；插件架构第一天就留好，但第三方生态放到最后。

### 1.4 选型调研结论（外部项目，用于解释 §3.4 的取舍）

- **OpenViking**（`volcengine/OpenViking`，字节火山引擎）：★40,240，**创建于 2026-01-05**（不到一年），最新 v0.5.0（2026-10-09）。
  许可证 **AGPL-3.0**，且 README 明确禁止「整体改写后再开源」、禁止「整体翻译成另一种语言」（需书面授权）。
  形态是**必须独立运行的 HTTP 服务**（FastAPI + uvicorn，默认 `127.0.0.1:1933`），依赖树含 scrapy / trafilatura / pdfplumber / litellm / tree-sitter×10 / OpenTelemetry 全家桶，构建需 maturin + cmake。
  **存储没有 SQLite 选项**，是「AGFS/RAGFS + Vector Index」双层。
  值得**借鉴设计、不引入依赖**的是它的分层上下文：L0 `.abstract.md`（256 字符，用于检索粗筛）/ L1 `.overview.md`（4000 字符，用于 rerank 与导航）/ L2 原文按需读；以及 `viking://` 虚拟文件系统把 resources / memories / skills 统一寻址的思路。
- **「字节最近又出了一个开源记忆」的排查结果**：把 `bytedance`、`ByteDance-Seed`、`volcengine` 三个组织的仓库按创建时间与 star 逐条扫过后，候选是——
  | 候选 | 事实 | 判定 |
  |---|---|---|
  | **火山引擎记忆库 Mem0** | 火山引擎 2026-02 推出，定位「数字海马体」，自研 `Mem0g` 图基记忆架构（向量检索 + 图检索双路径），声称响应时间比全上下文输入降 91%；**兼容开源 mem0 生态**，是**托管云服务**而非开源仓库 | **最可能是你要找的**（字节系、名字就是记忆、时间较近） |
  | `ByteDance-Seed/TaskMem` | ★30，Apache-2.0，2026-05-29 建、**2026-06-02 后停更**，多模态 Agent 记忆策略 RL 论文代码 | 名字最像，但是停更的论文框架 |
  | `bytedance/deer-flow` | ★84,066，MIT，DeerFlow 2.0 自带 per-agent memory，且**已官方接入 OpenViking 作 memory manager** | 「框架自带记忆」这条路 |
  | `Tencent-Hunyuan/Hy-Memory` | ★725，**2026-10-15 创建**、仍在推，配 HY-WU 功能性神经记忆框架 | **时间最贴近，但厂商是腾讯不是字节** |
  - 结论：**字节官方在「记忆层」这个品类上，目前公开可查的只有 OpenViking 一个开源仓库**；「记忆库 Mem0」是云服务。这一条不阻塞任何决策——D13 已定自研，外部项目只作设计参考。
- 选型调研的关键结论（完整版落 `docs/TECH_SELECTION_MEMORY_2026-10.md`，引导本决议）：
  - `sqlite-vec` 至今是**暴力检索、无 ANN 索引**（官方文档明说设计目标是小设备）；10,000 条 384 维实测 p50 9ms / p99 12ms（5 并发），10 万条外推约 890ms。→ **一万条内不要引向量索引**，本项目的规模区间正好落在最舒服的段。
  - **FTS5 的中文硬坑**：默认 `unicode61` 分词器不切中文（整句变一个 token）；`trigram` 分词器**少于 3 个字符的子串查不到**，两字中文查询（「分词」「复习」）直接失效。→ 必须**入库前统一分词**，配 `unicode61 remove_diacritics 2`，`trigram` 只作兜底。
  - **最值得借鉴的设计是 Letta 的 MemFS**：记忆就是一个 git 仓库，每条记忆是 Markdown + YAML frontmatter，**目录级 `MEMORY.md` 索引控制什么进上下文**——用目录约定替代「让 LLM 生成 L0/L1 摘要」，省 embedding、省 VLM、零延迟、可 git 回滚、可人工编辑。
  - **OpenViking 的 memory 类型划分可直接抄 schema**：`profile` / `preferences` / `entities` / `events` / `experiences` 等。
  - 许可证红线（影响 D13 与 D16）：OpenViking **AGPL-3.0** + 两条非标准限制（禁止整体改写后再开源、禁止整体翻译成其他语言）；Khoj、Reor 同为 AGPL；**FFmpeg 必须只用 LGPL 部分**（不带 libx264/libx265）；Whisper 权重 MIT 可用，pyannote 的说话人分离模型有非商用限制。
  - 本地模型选型（D14 / D16 的落地依据）：向量化首选 **Qwen3-Embedding-0.6B GGUF(Q8_0)**（中文强、有官方 GGUF、与 whisper.cpp 共用 ggml 基础设施），低配保底 **bge-small-zh-v1.5（192 MB）**；语音首选 **whisper.cpp large-v3-turbo Q5_0（574 MB，MIT）**，低配 small Q5_1（190 MB）；OCR 在 macOS 走**系统 Vision**（零体积），Windows/Linux 走 PaddleOCR(ONNX)。

## 2. 你要的东西（原始诉求转写）

> 「我刷 B站、抖音、小红书、微信公众号、视频号，看到 AI 相关或别的要学的内容会收藏，但它在手机里没法用……
>  X 上的内容、GitHub 上的优秀开源项目、我随时冒出来的灵感、微信读书里看到的、各种文档、skill……
>  这些东西都是零散的。我想做一个知识库，能实时接收我的灵感，也能实时接收各个来源的知识，把它们汇总，
>  定期做整理、给出报告，然后根据这个用 AI 分析给建议。
>  它还能打通平台壁垒——可以跨端，还可以自己设云端（我自己搭服务器，或者将来做收费同步服务）。
>  现在先不管，先本地离线，然后我自己搭服务器，再多端来弄。
>  多种剪藏来源：页面剪藏、Word / Excel / PPT 导入、语音输入、手打一个闪念胶囊……
>  它变成我的第二大脑，我有什么问题可以问它。随着知识库越来越多肯定会臃肿，
>  但它要能帮我做分类、做整理、做索引。像 RAG 这种东西要不要放进去考虑？
>  不能太卡，不能占资源太大。存储可以大，但不能一份东西复制很多次，一定要考虑内存、硬盘、CPU 占用。
>  轻量一点，但轻量不能丢精度和性能。」

## 3. 已拍板的决策（本轮 8 轮问答，全部经你确认）

### 3.1 产品与范围

| # | 决策 | 取舍理由 |
|---|---|---|
| D1 | **核心形态：卡片式知识胶囊**（原子卡片 + 标签/主题 + 智能回顾），不做长文档编辑器、不做纯阅读器 | 贴合「零散碎片 → 汇总」的输入现实 |
| D2 | **核心场景：极速收集 → 结构化整理 → 检索与温故** | 你的信息入口有 7+ 个平台，收集摩擦是当前最大杀手 |
| D3 | **AI 与开箱即用的关系：本地功能独立可用 + AI 作为增效外挂** | 分发给别人时不能一上来就要求填 Key；同时你个人的用法是强 AI |
| D4 | **首发主攻桌面端**（Windows / macOS），Android / iOS / Web 后续辐射 | Tauri 打包链已存在；手机端雷达后置 |
| D5 | **收集交互：全局闪念胶囊 + 智能链接嗅探 + 文档拖拽解析** | 一击可达，不打断当前工作流 |
| D6 | **抗臃肿机制：Inbox 收集箱 + AI 自动归档 + 周期性认知简报** | 保留人工复核口，避免 AI 归档错了无从纠正 |
| D7 | **旧刷卡/测验/FSRS 降级为「温故知新」独立子模块**，官方插件，**默认关闭** | 保住既有算法资产，又不让新用户一上来看到考试感 |

### 3.2 技术与架构

| # | 决策 | 取舍理由 |
|---|---|---|
| D8 | **检索架构：SQLite 混合检索**（FTS5 全文 + 向量语义 + 融合） | 单文件、嵌入式、不复制数据、内存可控 |
| D9 | **存储层升级为 SQLite 嵌入式数据库** + 开放格式导出备份 | 单文件 `cards.json` 撑不住万级条目 |
| D10 | **三层数据模型：素材 → 原子知识卡 → 生成产物** | 解决「AI 提炼有损」的焦虑，支持重新提炼；素材层永远可回溯原文 |
| D11 | **保留策略：按来源分别配置**（默认重索引轻原件，大媒体不存原文件） | 落实「存储可以大，但不能一份东西复制很多次」 |
| D12 | **图片/截图 OCR、语音转文字、视频字幕/转写、剪贴板监听提醒** 全部纳入范围 | 脚本做不到的模态正是 AI 的价值区 |
| D13 | **自研嵌入式记忆层**，不引入 OpenViking / mem0 等外部引擎 | AGPL-3.0 阻断未来闭源商业分发；独立服务进程与 3.2 GB 级别的依赖树与「轻量」目标冲突（见 §1.4） |
| D14 | **AI 分层：本地小模型做向量化，云端模型做生成** | 冷却成本与隐私，同时保效果 |
| D15 | **AI 接入：主流厂商一键预设 + 自定义 OpenAI 兼容端点 + 连通性测试** | 当前只有三个裸输入框，分发门槛过高 |
| D16 | **重能力按需下载**（语音 / OCR / 向量模型首次启用时引导下载，带体积与进度） | 安装包保持几十 MB |
| D17 | **产品基础能力离线可用，AI 只做增值** | 无网、无 Key 也不能是一片空白 |

### 3.3 交互与插件

| # | 决策 | 取舍理由 |
|---|---|---|
| D18 | **三栏工作台**：左导航/收集箱/标签，中知识流与速查，右详情编辑 + AI 问答侧栏 | 生产力场景的标准解，配合胶囊随时呼出 |
| D19 | **全局快捷键呼出居中悬浮胶囊窗口**（系统常驻托盘，记完即走） | 参考 Raycast 的即刻性 |
| D20 | **插件架构先行，官方插件先跑，第三方生态后开** | 你要模块化，但先做生态会拖死主线 |
| D21 | **插件运行时：独立进程沙箱 + 清单声明权限**（网络/文件/剪贴板/读卡库），单插件崩溃不影响主程序 | 分发给别人时，安全与稳定性是底线 |
| D22 | **术语拆成两类**：「技能/模块」= 可开关的功能插件包；「AI 技能」= 给 AI 的可复用指令与工作流模板 | 防止与 agent 领域的 Skill 概念混淆 |
| D23 | **第二大脑是「可执行型」**：能问答、能综合、能生成简报，也能调工具主动收集 | 你要的是能出去找资料的助理，不只是检索框 |
| D24 | **主动收集两种模式都要**：对话内按需联网找料（只推荐候选，一键确认入库）+ 订阅源定时入库 | 「只推荐不静默入库」把误入库风险挡在门外 |
| D25 | **订阅源优先级**：RSS / Atom、GitHub 动态（Release / Star / 趋势）、技术社区热榜（HN / Reddit / V2EX）；社交平台账号追踪（X / 公众号 / B站 UP / 小红书）成本与失效风险高，单独评估 | 先做合规、稳定、低成本的源 |
| D26 | **简报形态：固定三块** —— ① 本周收了什么（按主题聚簇，带原文链接）② 哪些主题在重复出现 ③ 值得回看的旧内容（时间衰减挑选） | 避免变成垃圾推送 |

### 3.4 工程与交付

| # | 决策 | 取舍理由 |
|---|---|---|
| D27 | **以 `apps/workbench` 为底座重构**（继承壳、打包链、存储、剪藏规则表、跨端契约），界面层与领域层按新模型重写 | 存量资产中剪藏规则表与三端打包 pipeline 价值最高 |
| D28 | **多端同步：现在不做，数据模型预留**（全局 ID、修改时间、墓碑标记、可合并结构） | 将来接自建服务器或商业同步时不重写数据库 |
| D29 | **导出四件套**：Markdown + 附件目录、完整 SQLite + JSON 备份、旧 `cards.json` 兼容导出、**往返无损**（有自动化护栏） | 用户把数据托付给你，必须随时能搬走 |
| D30 | **先整理干净 Git 基线，再开始重构** | 见 §1.2，`apps/workbench` 完全未入库是当前最高风险 |
| D31 | **先写齐设计文档再动代码**（ADR + 数据模型 + 插件规范 + 路线图） | 这次转向的幅度值得先固化 |

| D33 | **品牌改名，M1 阶段末尾再定名**；代码内部先用中性包名避免后期改名成本 | 命名不阻塞开发 |
