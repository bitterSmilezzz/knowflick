## 二、CI 覆盖矩阵

实际在跑的只有两个 workflow，各自独立：

| 环节 | macOS workflow | Android workflow |
| --- | --- | --- |
| runner | `macos-15` | `ubuntu-latest` |
| 触发 | push `main`（路径过滤）/ tag `v*` / 手动 | push `main`（路径过滤）/ 手动 |
| 单元测试 | ✅ 175 项 | ✅ 77 项 |
| 静态检查 | shell 陷阱检查 | Lint（0 错误 / 8 警告）+ shell 陷阱检查 |
| 构建 | 打包 `.app`（Xcode 26.3） | `assembleDebug` |
| 产物校验 | 签名、资源完整性（214 卡 + 42 图）、启动自检 | APK 内资源（种子卡 + 42 图）、版本号 |
| 产物分发 | tag 时自动附到 Release | 仅上传 artifact |
| 耗时 | ~3 分钟 | ~2.5 分钟 |

两个 workflow 都在 2026-09-14 升级到 Node.js 24 版本的 action，弃用警告已清零。

### CI 未覆盖的部分

1. **Android 仪器测试（28 项）不在 CI 中**。它需要模拟器，而 Gradle 的 UTP 会忽略 `ANDROID_SERIAL`——多设备同时连接时结果不确定。本地跑需先确保只连接一台设备。
2. **Android release 签名包不在 CI 中**。需要 keystore 与 `signing.properties`，属敏感凭据，需通过 GitHub Secrets 注入后再启用。当前 CI 只出 debug APK，避免把 debug 包误当发布产物。
3. **mac 启动自检是「不崩」而非「可用」**。CI 用无 GUI 会话跑二进制，只匹配 `could not load resource bundle` 这一条致命错误；窗口渲染、交互无法验证。

## 三、本轮（2026-09-14）修复的缺陷

按影响面排序：

### 1. 已发布版本启动即崩（最严重）

mac **v3.2.0 对所有下载者都是启动即崩**。Release 上的 zip 与本地 9-11 产物字节相同（sha256 `b9dab505…`），崩溃栈为 `AppStore.loadSeedCards() → NSBundle.module → assertionFailure`。

根因：SwiftPM 生成的 `resource_bundle_accessor` 在不同工具链下候选路径不同——CommandLineTools 会查 `Bundle.main.resourceURL`，Xcode 查 `Bundle.main.bundleURL` 与编译期 `.build` 路径，于是「本地能跑、发布出去崩溃」。已在 v4.2.0 修复（`CoreResources` 自行按候选列表查找），并补上启动自检防复发。详见 [macOS 4.2.0 发布记录](MAC_RELEASE_4.2.0.md)。

v3.2.0 的 Release 已加警告说明，产物保留仅作历史可追溯。

### 2. 构建脚本会删除上一版成功产物

`build_app.sh` 的 EXIT trap 无条件清理，构建失败时会连带删掉上一次的成功产物。已改为只清理本次运行创建的内容。

### 3. shell 变量名被全角标点吞并

`$VAR）` 这种写法会让 bash 把全角括号的首字节并入变量名，在 `set -u` 下直接 `unbound variable` 退出。只在 UTF-8 locale 的 bash 下触发，zsh 与 C locale 都不复现——**本地极易漏过，到 CI 才炸**。该坑在 mac workflow 与 android workflow 各踩一次，现已固化为 `tools/lint_shell_vars.sh` 并接入两个 workflow。

### 4. 测试脚本在缺 Xcode 时完全不可用

本机只有 CommandLineTools，`swift test` 会因 KnowFlick 执行文件依赖 SwiftUI 宏而失败，导致 175 项 Core 测试一个都跑不了。新增 `--core-only` 绕开该依赖。同时修掉两个自身缺陷：Swift Testing 宏插件路径缺失导致的**间歇性**构建失败（同一命令重复运行会时好时坏），以及缺宏插件时抛 487 行错误、真正原因被淹没。

### 5. 版本号跨端借用

CHANGELOG 中 `v4.1.1`–`v4.1.8` 这 8 条记录实为 Android 里程碑（M1–M7），已更名为对应的 `android-v0.1.0`–`v0.7.0`。mac 自 4.2.0 继续，两端序列自此互不相干。

### 6. 零散清理

- `.gitignore` 里重复的 Python 段落已合并（无功能影响）。
- README 目录树过时描述修正：`Resources/` 不再写「符号链接」，`Bundle.module` 改为 `CoreResources.bundle`。
- `docs/MULTI_PLATFORM.md` 同步修正共享资产引用方式的描述。

## 五、Windows 端：已评估，暂缓

已完成技术栈调研与实测（详见下方结论），**决定搁置，后续直接在 Windows 真机上开发**。保留结论供将来参考。

在 macOS 上实测的候选栈能力：

| 候选 | macOS 上能跑起来看界面 | macOS 上能构建 Windows 产物 |
| --- | --- | --- |
| **Avalonia**（.NET） | ✅ 原生窗口 | ✅ `PE32+ executable (GUI) x86-64`，单文件 84.9 MB |
| WPF | ❌ 无法运行 | ✅ 可编译（需 `EnableWindowsTargeting`） |
| WinUI 3 | ❌ | ❌ 需 Windows SDK |
| Flutter | — | ❌ 实测报 `"build windows" only supported on Windows hosts` |
| Tauri | 需装 Rust | ⚠️ 官方文档称跨平台编译为「last resort」，仅 NSIS 实验性支持 |

附带确认：Avalonia 的渲染底层 SkiaSharp 能解码项目全部 42 张 WebP（逐张真实解码像素，42/42 通过）。

若将来选 Avalonia，主要成本在三处：**代码签名的钱与流程**（未签名会让多数用户止步于 SmartScreen；EV 证书自 2024 年起已无免警告优势）、**中文 IME 与字体的真机调优**（默认字体不含 CJK 字形且不支持逗号回退链）、**Windows 专属问题在 Mac 上看不见**（macOS 后端与 Win32 后端是两套实现）。

若在 Windows 真机上开发，WinUI 3 重新成为可行选项（原生控件、系统观感最好），代价是只能在该机器上开发和验证。

## 七、共享资产

`shared/assets/` 是种子卡与底图的**唯一事实来源**：

- `seed_cards.json`：214 张种子卡
- `bg/*.webp`：42 张分类底图（WebP 格式，Android 端包体因此减半）

两端通过不同机制引用：mac 用 `tools/sync_shared_assets.sh` 同步进 SwiftPM 资源目录（该目录不入 Git），Android 用 Gradle 的 `assets.srcDirs` 直接指向共享目录。
