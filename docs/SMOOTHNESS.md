# 丝滑清单：把「卡一下」的地方逐个拆掉

> 目标不是「功能存在」，而是**每一步都不卡、不猜、不等**。
> 这份文档记录已经量过／修过的地方，以及实测后判定**不需要动**的地方。

### 规模冒烟的时间断言在乱报——它测的不是界面

`scale_ui_smoke` 的「单次按键阻塞 < 150ms」反复失败。查下来**不是界面慢**，
是**测量方法不可靠**，连着踩了四个坑：

| 坑 | 现象 | 结论 |
| --- | --- | --- |
| 机器调度抖动 | 同一份代码、同一操作，单次测量从 **17ms 到 165ms** | 绝对毫秒数在这台机器上不可用 |
| 搜索词**重复** | React 复用上次的渲染结果，后续测量又快又不稳 | 每轮必须用**不重复**的词 |
| 页面反复重载 | 测的是「冷启动」路径，不是稳态打字 | 测量与打开耗时分开 |
| 轮数太多 | 退化时直接被 agent-browser 超时杀掉（`killed: true`） | 断言要能**判失败**，不能靠超时 |

修法：8 轮 × 4 次不重复的词，取 **p90**（p50 受抖动影响大），
预算按**实测**定（本机 4000 条时 p50≈135ms / p90≈173ms，预算 300ms）。

**反向验证**（把过滤退化 40 倍）：

| | p50 | p90 | 结果 |
| --- | --- | --- | --- |
| 正常 | 135ms | 173ms | 通过 |
| 过滤退化 40 倍 | 298ms | **431ms** | **失败**：「p90 431ms 超过预算 300ms」 |

> 这一轮我先后用三个「看起来更聪明」的判据都失败了：比值判据（大小库之比）
> 抓不到退化；「多轮取最小」会把真退化一起掩盖；绝对毫秒数直接被噪声顶穿。
> **只有先量准分布、再定预算、最后用反向验证确认它能失败**，才算数。

顺带的三条否定结论（都是查过之后**证伪**的假设，省得以后重查）：

- **没有性能退化**：历史提交与当前版本用**同一探针**测，p50 分别是 18ms 与 14ms。
- **没有「阈值效应」**：上一版记的「500 条持平、2000 条跳到 3 倍」是**噪声**。
  在**同一会话内**扫 500 / 1000 / 1500 / 2000 / 2500 / 3000 / 4000 七档，
  p50 分别是 91 / 26 / 154 / 144 / 160 / 144 / 163ms——**基本持平**，
  1000 条那档反而最低。耗时与库规模**无关**。
- **读区重渲染不是瓶颈**：`EntryInspector` 每次按键确实会重跑（它没有 memo，
  且 `selected` 会随查询变化），但交替实验（normal 与「固定 selected」
  各跑三次）显示两者无显著差异（57/105/91 对 80/70/67）。

顺带量到的：过滤 2000 条只要 **3ms**、`entriesFor` 只要 **1ms**、4000 条排序
（`localeCompare`）只要 **0ms**——真正花时间的地方**没有定位到**。
空白页做同样的动作是 0ms，所以这 60–160ms 确实是应用自己的开销，
但既不随规模增长，也不是读区。**如实记下，不编原因。**

### 「存进去的附件读回来对不对」从来没被验过

附件链路（录音 / 手写 / 图片）看着是齐的：Rust 侧 `save_media` / `read_media`
有测试，库表 `media_path` 的往返也有测试。

但**前端那一环是空的**：`EntryInspector` 读回附件的逻辑活在 `useEffect` 里，
而它的测试用 `renderToStaticMarkup`——**服务端渲染，不跑 effect**。
所以「宿主读回来的字节有没有原样变成 Blob」这条**从来没被执行过**。

修法：把这段逻辑抽成纯函数（`ui/workspace/attachment.ts`），不依赖 DOM、
不依赖 Tauri，node 环境下就能测：

- `attachmentMime` —— 以存盘时记下的 MIME 为准，缺了按来源类型兜底，`metadataJson` 坏了也不崩
- `attachmentBlob` —— 宿主回来的 `number[]` **原样**变成 Blob（附件是用户自己录的，不能被悄悄改）
- `inlineImageUrl` —— 浏览器体验里的内嵌图片只认 `data:image/` 开头
- `hasReadableAttachment` —— 「有 `mediaPath`」不等于「附件还在」

**四条断言都反向验证过**：抹掉读回字节的最后一个 → 字节断言失败；
MIME 写死 → MIME 断言失败；内嵌图片不查前缀 → 前缀断言失败。

顺带修了一个真问题：`new Blob([uint8])` 在 TS 严格模式下**不合法**
（`Uint8Array` 的 buffer 可能是 `SharedArrayBuffer`），现在显式拷进新的 `ArrayBuffer`。

> 教训：测试用 SSR 渲染组件时，**只有渲染结果被验了，effect 里的行为一片空白**。
> 关键路径的逻辑要抽成纯函数，测试环境才盖得住。

### 真机验证卡在锁屏——而且原工具会给「假通过」

连着两轮把真机逐页验证记成「环境限制未做」。查下来，**原因确实是锁屏**，
但**前两轮对机制的理解都是错的**：

| 屏幕状态 | `System Events` 读窗口 | `cliclick` 点击 | `screencapture -R` 裁窗口 |
| --- | --- | --- | --- |
| 解锁 | ✓ | ✓ | ✓ |
| **锁屏** | ✗（`-1719` 无效的索引） | **✓（事件照样投递）** | ✗（`could not create image from rect`） |

于是最坏的一种情况出现了：锁屏时**点击照常生效**，但截到的是**锁屏界面**
（带时钟，每秒都在变）——像素比对于是**永远**判定「页面变了」，
脚本一路报「真机上点开某页且内容确实变了」。

> **那是假通过，而且是最坏的一种**：看起来有证据，其实什么都没验。
>
> 我自己写的探针就栽在这里——它报告「内容变化: true」，而两张图我一看
> 分别是 10:53 与 10:54 的**锁屏时钟**。

修法：`real_app_pages.mjs` 先查 `CGSSessionScreenIsLocked` / `ConsoleLocked`
（`ioreg -n Root -d 1 -a` 里有这个键就是锁着），锁屏就**如实 SKIP 并说明原因**，
不给假通过。

判锁屏的小坑：`ioreg` 的输出是 XML 转义的，按普通子串找键名容易漏；
稳妥做法是 `raw.includes("CGSSessionScreenIsLocked")`。

顺带记清楚两件**不是**问题的事（省得以后重查）：

- **桌面壁纸那套说法是错的**：屏幕确实锁着（`loginwindow` 在跑、
  截屏看得到「输入密码」框），不是「桌面壁纸刚好长这样」。
- **点击在锁屏下是有效的**：`cliclick` 事件照样投递给应用，
  所以「窗口开不了 / 点不动」都不成立；卡住的只有**截图**。

真机逐页验证本身是能做的：解锁状态下跑 `real_app_pages.mjs`，
5 项全过（认知简报 / 产物库 / 统计 / 知识测验，每项都做内容区像素比对）。

### 模态内的控件也要有可见焦点环

键盘用户能 Tab 到某个控件却**看不见焦点在哪**，等于没有焦点。门禁原先只查
主界面（`Tab 顺序可达 N 个控件，全部有可见焦点环`），模态内的控件没查。

现在补上：打开语音面板后用**真实 Tab 按键**走一圈，量每个被聚焦控件的
`outline`/`box-shadow`。

> 关键：不能用 `el.focus()` 测。编程式聚焦**不触发** `:focus-visible`
> （那是给键盘导航用的），测出来全是「无焦点环」的假象——
> 我第一版就是这么测的，四个按钮全报无环，实际用 Tab 测每个都有 2px 实线。
> **测量方式错了，结论就全错。**

**反向验证过**：去掉 `.ws button:focus-visible` 的 outline，断言立刻报
「11 个可聚焦控件没有可见焦点环」（主界面 + 面板内一起被数到）。

顺带的否定结论：面板内控件的 DOM 顺序与视觉顺序一致（关闭在顶部第一行），
打开时焦点落在「关闭」上——都是对的，不需要调整。

### 手写/语音面板键盘完全进不去

同一个界面里，「记录」模态用的是原生 `<dialog>`（`showModal()`），浏览器自动
给焦点陷阱与 Escape；而手写/语音面板是**手写的 div**，什么都没接上。

实测：打开语音面板后连按 12 次 Tab，焦点**始终在侧栏**——面板里的
「开始录音」「停止录音」「取消」「保存语音笔记」全部键盘不可达；Escape 也
关不掉面板（`onKeyDown` 绑在 backdrop 上，而焦点不在它内部，事件收不到）。

这与 `docs/UI_CONSOLIDATION.md` 里写的「全键盘完成检索、选择、编辑、保存、
关闭」直接冲突——键盘用户根本用不了手写与语音。

修法：新增 `useModalFocus` 钩子，把原生 `<dialog>` 的两项能力补到手写模态上：
打开时把焦点移进面板、Tab/Shift+Tab 在面板内循环、Escape 关闭、关闭后焦点
回到打开前的位置。

**Tab 循环是必须的**：面板是 `aria-modal` 的，底层界面**被视觉遮住但仍可聚焦**，
不循环的话 Tab 会走到看不见的地方——比走不进去更糟。

修后实测：打开面板焦点已在面板内；Tab 在「取消 → 开始录音 → 保存」之间循环；
Escape 能关闭；关闭后焦点回到「语音」按钮。

**反向验证过**：去掉焦点管理，门禁立刻报「打开面板后焦点应落在面板内」。

顺带的否定结论（省得以后重查）：录音的**取消、停止后取消、重录**三条路径都
正确释放了麦克风（轨道从 `live` 变 `ended`），取消不会留下「没有录到声音」
的错误提示——组件卸载后不再渲染。

### 浏览器录音组件：这条路径此前从未跑过

语音冒烟只验到「面板打开 / 准备录音 / 没有录音时不能保存」，
**录音流程本身一次都没跑过**——验收清单里那条空白就是这么来的：
没有麦克风就没法测。

解法：Chrome 的 `--use-fake-device-for-media-stream` 提供**合成音频输入**，
不需要真硬件、不需要麦克风权限，CI 与普通开发机都能跑。

现在验到：开始录音 → 计时**真的在前进** → 停止 → 「录音完成」→ 可回放 →
可保存。两条关键断言都做了**反向验证**：

- 去掉合成输入参数 → 「按下后进入录音状态」立刻失败；
- 把录到的字节换成损坏数据 → 「能解出真实时长与采样率」立刻失败。

第二条是这轮补的：之前只验「字节非零」，但**非零字节也可能是垃圾**。
现在用浏览器自己的 `AudioContext.decodeAudioData` 解一次——
能解出时长与采样率，才说明录到的确实是一段音频。

同样地，模型输出的边界用例也从「类型不对不报错」收紧到
「不生成链接」（`links` 为空数组）——原先那版断言的是「links 是数组」，
而它**恒为数组**，等于没断言。

> 教训：「需要外部条件」不等于「没法验」。麦克风可以用合成输入替代，
> API key 可以用假端点替代——**先问条件能不能造出来**，再说做不到。
>
> 但也要说清**替代品的边界**：合成输入证明的是浏览器录音组件可用，
> **不等于**物理麦克风、系统权限与桌面保存已验收。

浏览器体验**不保存录音**（产品设计：界面说明「浏览器体验不保存录音，请在桌面
客户端使用语音笔记」），所以桌面那一步仍需真机。

### 同一屏两个入口做同一件事（文字不同，重复 CTA 检查抓不到）

品味门禁有一条「同一屏没有重复 CTA」，但它**按按钮文字**计数——所以
「记录 ⌘N」（侧栏）与「记录第一条」（中栏列表空态）抓不到：**它们做的是同一件事**
（都调 `setCapture(true)`，都打开记录面板）。

用户看到两个入口以为是两件事。改法：中栏空态不再放「记录第一条」——
侧栏那个**常驻可见**且带快捷键提示；中栏改成文字引导「侧栏的『记录』随时可以写一条」。

同时给门禁补一条**按动作**的检查（不按文字），并把首屏引导断言从
「某个按钮的文字」改成「引导说了什么」——按钮位置会随界面收敛调整，
引导不能跟着消失。**严格反向验证过**：去掉引导标题与说明，断言立刻失败。

> 教训：按**文字**找重复，只能抓到字面重复。按**动作**才算数。
> 同一件事的不同措辞，往往是重复 CTA 藏得最深的地方。

### 导入失败时提示条上挂着「重新读取」

错误提示条有一个「重新读取」按钮——它只对**读取失败**有意义。但同一套提示条还用于
导入失败、转换失败、导出失败、备份恢复失败（共 11 处 `setError` 调用）。

于是用户导入失败后看到「重新读取」，点了只会**重载库**——与他的问题无关，
还会打断他正在做的事。

改法：区分错误类型。只有「读取知识库失败」才显示「重新读取」，其余只给关闭。
新增断言：导入失败时提示条里不能出现「重新读取」。**反向验证过**：把按钮改回
无条件显示，断言立刻失败。

> 教训：一个共用的提示条上，**每个按钮都要对得上当前的错误类型**。
> 「顺手放一个万能按钮」在失败路径上尤其误导——用户正着急。

### 「清空搜索」按钮其实也清掉了标签

空列表时的提示写着「换个关键词，或清空**筛选**看看全部内容」，而按钮上写的是
「清空**搜索**」——但它执行的是 `setQuery(""); setTag("")`，**标签也一并清了**。
用户点完发现标签筛选也没了，而按钮没说。

改成「清空搜索与标签」，并加断言锁住：按钮文案必须同时提到搜索与标签。
**反向验证过**：改回旧文案，断言立刻失败。

> 教训：按钮文案要覆盖它**实际做的全部事**。少说一件，用户就多一次意外。

### Linux job 连续两次超时——卡在 apt，不是门禁

`Workbench (Web + Tauri)` 在 Ubuntu runner 上连续两次被判超时取消。查 step 时间戳：

| Run | apt 步骤 | verify 步骤 | 结果 |
| --- | --- | --- | --- |
| `39842202918` | **48 秒** | 3 分 05 秒 | success |
| `39846955126` | **25 分（卡死）** | 未执行 | cancelled |
| `39851958477` | **25 分（卡死）** | 未执行 | cancelled |

两次都卡在第 3 步「安装 Linux 系统依赖」，**跑 verify 的那一步根本没开始**——
所以这不是「门禁太重」，是 Ubuntu runner 的 apt 源偶发不响应。同一时刻
Release workflow 的 Linux job 成功，进一步说明是环境抖动。

修法两处：

- 超时上限 25 → 45 分钟（release 45 → 60，它要打三平台包）；
- apt 调用加 `Acquire::http::Timeout=30` 与 `Acquire::Retries=2`，外层重试 3 次、
  每次间隔 15 秒——**失败要快，恢复了就继续**。

> 教训：**先看 step 时间戳，再下结论**。我一度以为是自己新加的对照脚本太贵
> （它第一版确实会触发 Rust 全量重编，那是真问题，已改成常驻探针），
> 但真正让 job 报废的是 apt。两者都改了，但只有后者是这次超时的主因。

### 回环判定三端不一致（同一份 settings.json，两端行为不同）

回环判定散落在三处，各写一套字符串比较：

| 位置 | 原写法 | `0:0:0:0:0:0:0:1` |
| --- | --- | --- |
| 桌面壳 `http.rs` | `Ipv6Addr::is_loopback` | ✅ 回环 |
| 桌面前端 `ingest.ts` | 字符串比 `"[::1]"` | ❌ **不是回环** |
| 安卓 `SpeechSettings` / `AiProviderPresets` | 字符串比 `"::1"` | ❌ **不是回环** |

于是同一份 `settings.json` 里写着 `http://[::1]:11434/v1` 时，桌面端认它是本机
（免密钥、允许 HTTP），安卓端不认（要密钥）。这正是 ADR-0002 §3 要避免的：
**同一份文件在两端行为相同**。

现在三处统一走同一套口径（127.0.0.1 / localhost / IPv6 回环）：

- 桌面壳 `is_loopback_host`：交给 `Ipv6Addr::is_loopback`；
- 桌面前端 `isLoopbackHost`：按八组解析 IPv6 字面量（**不用 `::` 压缩语法**——
  `0:0:0:0:0:0:0:1` 里根本没有 `::`，按压缩写法判断会漏掉它）；
- 安卓 `LoopbackHost`：同样按八组语义，只认**恰好** `::1`，
  `::ffff:127.0.0.1` 这种 IPv4 映射写法不算（Rust 端也不认）。

新增 `tools/check_loopback_parity.mjs`：同一批 16 个地址跑过 Rust 与 TypeScript
两套实现，逐条比对，不一致就失败。**反向验证过**：把 TS 判定改窄，它立刻报出
`"127.0.0.1"：Rust=true TypeScript=false`。安卓那侧由镜像用例
`LoopbackHostTest.kt` 保证（同一批地址，8 项）。

> 这一条不是「某个端算错了」，而是**三端各自都对、彼此不一致**——
> 只有把两边放在一起比才会暴露。

对照脚本本身踩了两个跨平台坑（都只在 CI 上暴露，本地一律通过）：

| 坑 | 症状 | 修法 |
| --- | --- | --- |
| `spawn npx` 在 Windows 上 ENOENT | Windows 的 release 门禁红 | 用当前 node 直跑 `node_modules/vitest/vitest.mjs` |
| 解析要求行首是 `PARITY` | **三端一起红**：CI 上 vitest 给 console.log 加前缀并缩进 | 改成行内匹配 `PARITY\t…\t(true|false)$` |

第二个坑值得记住：**本地输出与 CI 输出格式不同**。本地 vitest 打印裸行，
CI 上是 `stdout | src/… > parity` 加缩进，按行首匹配时本地 16 条全中、CI 一条都不中。
这次是三端同时失败才暴露——单看某一端会以为是平台问题。

> 已用「CI 风格输出」复现验证：旧正则匹配 0 条，新正则匹配全部。
> **本地绿灯不等于门禁会绿**——脚本要按最严的环境假设来写。

第三个坑是**代价**：脚本原本临时改 `http.rs` 插探针，这会让 cargo **重新编译整个
crate 依赖树**——CI 上一轮门禁要多花十几分钟，实测把 Linux job 顶到 25 分钟上限
之外被取消（不是失败，是超时）。改成**常驻的对照探针测试**
（`http::tests::prints_loopback_verdicts_for_cross_platform_parity`），
cargo 只需增量编译；对照脚本本机耗时从「触发重编」降到 **0.8 秒**。

> 教训：门禁里的检查不能太贵。**贵到超时等于没有**——它不会报出问题，
> 只会让整条流水线卡住。

### 本地模型请求被送进代理（用户设了 HTTP_PROXY 时）

用户若在系统里配了 `HTTP_PROXY`（很常见），reqwest 默认把**所有**请求交给代理。
于是本地模型（`http://127.0.0.1:11434`、`http://[::1]:11434`）的请求被送到代理
而不是本机服务——连接测试报「抓取失败」，而用户完全看不出原因。

修法：按目标地址选客户端，**只有回环绕过代理**（`client_for` → `no_proxy()`），
外部地址照旧跟随系统代理——否则用户配的代理对剪藏外站就失效了，那是更大的问题。

回环判定交给 `Ipv6Addr::is_loopback`，`0:0:0:0:0:0:0:1` 这种展开写法也算。

> 这条来自只读复核：新加的 IPv6 用例在代理环境下失败。查下去发现**不只是用例
> 的问题**——生产路径同样受影响。复核代理给的判断是对的。

用例两条：
- `only_loopback_addresses_bypass_the_proxy`：纯函数判定，断言**范围精确**
  （回环绕过、外部不绕过）；
- `loopback_requests_bypass_ambient_proxy_settings`：真在本机监听，断言请求
  真的到达监听而不是被代理截走，带 5 秒超时保护（退化时快速失败，不挂十几分钟）。

**反向验证过**：移除代理绕过后，两条行为用例在清空 `NO_PROXY` 的环境下失败，
恢复后通过。默认环境与代理环境下各跑一遍，都是 12 项全过。

> 排查时踩到一个坑：本机 `NO_PROXY` 本来就含 `::1`，所以最初的复现**看不到**问题；
> 必须显式清空 `NO_PROXY` 才暴露。这提醒我：**验证环境与用户环境不一定相同**。

### IPv6 本地模型被误判成需要密钥

用户填 `http://[::1]:11434/v1`、不填密钥时，连接测试在发请求前就报
「未配置 API Key」。WHATWG URL 与 Rust URL 的主机名都保留方括号 `[::1]`，
代码却比较 `::1`，因此前端把本机模型当成公网，Rust 也拒绝本机 HTTP。

前端 `requiresKey`、`assertFetchableUrl` 与 Rust `validate_url` 改为识别规范化后的
`[::1]`。完整写法 `0:0:0:0:0:0:0:1` 同样规范化为此值；普通 IPv6 与 `[::]`
不因此获得本机豁免。

先复现再修：前端三条断言失败，Rust 本地地址断言失败；修后均通过。
前端回归走真实 `probeConnection`、`askModel` 与 `completeChat` 路径，仅替换网络
响应，断言请求地址、无 Authorization、模型参数和实际解析出的知识卡。
Rust 在临时 `[::1]:0` 服务上实际完成聊天、Embedding、网页抓取三种请求。
这些证据验证本地传输与守卫，不代表真实模型内容质量已验收。

## 一、已修：批量导入不再一错全废

**症状**：选十个文件、其中一个格式不支持，前面的导入了、后面的全不处理，
用户只看到一句「导入未全部完成」。

**原因**：`importFiles` 里任何一处 `throw` 都会跳出整个 `for` 循环。

**现在**：逐文件处理，结果分三桶——成功 / 与库里内容相同已跳过 / 失败，

## 二、已修：图片终于能作为来源

**症状**：用户把图片列为来源之一，导入却直接报「暂不支持这种格式」。

**现在**：`.png / .jpg / .jpeg / .webp / .gif / .heic` 作为独立素材类型入库；

阅读区直接显示图片。CSP 相应放开 `img-src` / `media-src` 的 `blob:`，

## 二·补：PPT 终于能导入

**症状**：用户把 `ppt` 列在来源里，导入只认 Word/PDF，遇到 PPT 直接报「暂不支持这种格式」。

**现在**：`parsePptxBuffer` 复用已有的纯 JS ZIP 解压器（不引入依赖），
取 `ppt/slides/slideN.xml`，按**编号**排序（按字符串排会让 `slide10` 跑到 `slide2` 前面），
提取 `<a:t>` 文本并按页拼成 Markdown。只取文字，不还原版式/图形/备注——
目标是能搜到、能被 AI 提炼。XML 实体会还原，纯图片 PPT 与「根本不是 PPTX」
分别给出可读原因。旧版 `.doc/.ppt/.xls` 明确提示「请另存为 .docx 等」。

**当前支持的来源**：

| 类型 | 状态 |
| --- | --- |
| Markdown / TXT / JSON | ✅ |
| Word (.docx) | ✅ |
| PowerPoint (.pptx) | ✅ |
| PDF | ✅ |
| 图片 (.png/.jpg/.webp/.gif/.heic) | ✅ 作为素材，不做 OCR |
| 旧版 .doc/.ppt/.xls | ❌ 提示另存为新格式 |
| Excel (.xlsx) | ❌ 尚未支持 |
| 邮箱 / 订阅源 / 剪藏 / 手写 / 语音 | ✅ 各自独立入口 |

**症状**：AI 归纳、转写、抓取订阅、恢复备份期间，界面只是按钮变灰，
状态栏永远显示「已保存到本机」——看不出在等什么，也没有退出的办法。

**现在**：

- 状态栏显示具体动作：`正在转写语音…`、`正在抓取「X」…`、`正在导入 3/8`、`正在恢复备份…`。

## 四、已修：内容去重

**症状**：`contentHash` 字段从建库起就存在，但**从未被赋值、也从未被检查**，
所以同一个文件导入两次就是两份重复素材。

**现在**：`contentHashOf` 用 FNV-1a 32 位 + 长度前缀（不是密码学哈希，只用于去重），
忽略行尾与首尾空白，空内容不生成指纹。图片按「文件名 + 字节数」判重。

## 五、已修：搜索覆盖（「明明有却搜不到」）

搜索是最常用的动作，覆盖不全就是最难受的卡点。**先写测试证明缺口，四条当场全失败**：

| 缺口 | 现象 |
| --- | --- |
| 卡片只搜 `details`，**不搜 `summary`** | 用户记住的往往正是那句结论，却搜不到 |
| 卡片只搜 `links[0]` | 从第二条链接起搜不到 |
| 邮件标为 `tags: []`，正文里没有发件人 | **按发件人搜不到** |
| 附件名不在任何搜索字段里 | 搜附件名搜不到 |

修法：

- 素材搜索文本摊平 `cleanedMarkdown` 与 `metadataJson` 里的
  `from / to / subject / fileName / mime / attachmentFilenames`。
  **坏元数据退回只搜正文**，不让整条素材从结果里消失。
- 卡片搜索文本包含 `summary + details + 全部链接标题与地址`。
- 顺带补上 `image / audio / ink` 三种来源的中文分类名（之前全显示「闪念」）。
- 占位文案改为「搜索标题、正文、发件人、附件或标签」，与实际覆盖一致。

**性能核对**：`entriesFor` 现在会解析 `metadataJson`，但它是按
`[materials, cards, collection]` 记忆的，不会随每次击键重算。
实测 200/1000/3000 条打开到可交互仍是 ~357 ms，与改动前一致，无回归。

## 六、已修：温故复习的两处自相矛盾

查复习页时发现两件事叠在一起：

1. **`dueOnly` 默认 false**，复习页把所有卡都排进队列——「今日待复习 0」下面紧接着
   出现一张待评分的卡，计数与界面自相矛盾，FSRS 排期也形同虚设。空态有文案，
   但**没有任何出口**。
2. 只把 `dueOnly` 打开会引入更严重的问题：`reviewDay` 对「从未看过」的卡返回 `null`，
   新卡因此**永远不算到期**——新建的卡再也进不了复习队列，库越攒越多却一次都没复习过。

修法：

- 新增 `reviewQueue` = **到期卡在前、从未过目的新卡在后**（两类含义不同：到期是
  「该看了」，新卡是「还没看过」），并受上限约束（默认 20）。
- 复习页改用 `reviewQueue`；空态文案说明「记忆算法已把 N 张卡排到之后」，
  并给显式出口「仍要复习全部（额外练习）」——只有额外练习才用全库队列。

## 七、已修：备份不带附件（最重的一项）

**症状**：设置页写着「数据完全归你所有」，但 `.kfbackup` 只打包 `materials.json`
里的 `mediaPath` 字符串，**从不带媒体字节**。换一台机器恢复后那些路径指向空处，
阅读区读取失败又静默不显示——用户以为备份完整，实际录音与图片已经丢了。

**修法**：

- 打包：附件按库内相对路径作为 ZIP 条目一起带走，`manifest.stats.media` 记数量。
- 解包：新增 `unpackZipStoreBinary` 保留原始字节（文本解码会把音视频搅坏）。
- 还原：只接受 `media/(audio|image|ink)/` 白名单路径，备份包里夹带的越界路径一律不还原；
  按扩展名还原白名单 MIME 再落盘（用 `application/octet-stream` 会被类型白名单全部判失败）。
- 导出：逐条读字节，**单条缺失只跳过该条**，不阻断整份备份；完成提示带上附件数量。

同轮顺带修的潜伏缺陷：

- `saveMedia` / `readMedia` 写死 `dir: null`，自定义库目录时附件会写到默认库；
  现在与其它 shell 调用一样透传 `dir`。
- 附件读取失败不再静默留白，提示「附件没能读取（可能已被移动或删除）」。

## 七·补：应用阶段——批量操作与「点了没反应」

### 批量操作

产品要求里写过「对知识做应用做总结做一系列操作」，但列表一直是**单选**：
点谁选谁，整理几十张卡只能一张张点。

- ⌘/Ctrl（Shift 也接受）点击追加或取消；普通点击仍是单选并**退出多选**。
- 换页 / 换筛选自动清空选择，不留看不见的待处理选择。

### 问答的对话一离开就清零

`messages` 只是 `useState`，没有任何持久化：问几句、切到别的页面再回来，
整段对话就没了。问答是应用阶段的核心，问完就忘等于每次从零开始。

- 对话存到本机（`knowflick.workspace.chat`），**切页、刷新、重启后都还能接着问**。
- 读取时逐条校验：坏数据、空内容、非法 role 一律丢弃；整段坏掉就退回问候语，
  不让一条脏数据把问答页打不开。
- 只留最近 **40 轮**；写入失败（存储满）只放弃持久化，对话仍在内存里。
- 有对话时提供「清空对话」，并说明「对话会保存在本机」——有持久化就必须有清空的出口。

| 清理后第一次 `verify_workbench.sh` | **5 分 12 秒**（全量重编） |
| 之后的门禁 | Rust 测试本身 0.5–1.2 秒（产物已缓存） |

结论：清理**只是让下一次门禁慢几分钟**，不影响正确性（清理后 `exit=0`，
339 前端 + 84 Rust 全过）。护栏是「有 cargo / rustc / rust-analyzer / cargo-tauri
在跑就整轮跳过」，实测脚本会先探测再动手。

> 一次教训：连续多轮每轮都跑 `verify_workbench.sh`，产物会一直涨；
> 有自动清理就不用手动管，但要**确认清理后仍能跑通**（这一条我实测了）。

### 导出包会带走 settings.json 里遗留的密钥

界面写着「已导出完整备份包 (.kfbackup)，包含素材、卡片、设置与附件，**不含 API 密钥**」，

settings.json 里的**未知键原样带走**——那份文件里若留着密钥字段（用户手改过、
或旧版本写过），就会被打进**用户会分享/上传的包**里。

两端都只净化**导出路径**（不动正常读写 settings.json 的行为）：

- 前端 `stripSecrets`、Rust `strip_secret_settings`，同一套规则；
- 只认「名字像密钥」的键，**不做值层面猜测**——值层面的脱敏是错误信息的职责，
  这里防的是「字段本身不该被带出库外」；
- 名字里带 key 但正常的配置（`orderKey`、`searchKeywords`）**不误删**；
- 设置文件是坏 JSON 时**原样返回**，导出不因为设置坏了而失败。

同一轮还查了一处「看着像漏洞、查完不是」：CONTEXT.md 写「链接带 `user:pass@`
的直接拒，否则凭据会被写进卡片来源链接」——手动记录路径**是有校验的**
（`makeMaterial` 里 `parsed.username || parsed.password` 直接抛错，素材不落库）。
我先假设没校验去复现，结果发现校验在，复现脚本里素材数为 0。

### AI 错误原文回显密钥（两端都漏了）

查「AI 请求失败时用户看到什么」，发现凭据会泄露到界面：

```js
// 前端
throw new Error(`API 返回 ${status}：${text.slice(0, 200)}`);
// Rust
Err(format!("API 返回 {}：{}", status, text.chars().take(200)))
```

服务端错误原文直接进界面。而**部分服务商在 401 里会回显 API key**（OpenAI 会截断，
自建网关常常不截）——界面上的密钥一旦被截图或分享就泄露了。

同一份产品里两处相反的做法：邮箱侧早定了原则「错误不回显密钥——不把服务端
原文透给界面」（`docs/EMAIL_INTEGRATION.md`），AI 侧没有。**按项目自己的原则对齐。**

- 前端 `redactSecrets`：抹掉带前缀的 key（`sk-` / `rk-` / `gsk_` / `xai-` / `api-`）、
  `Bearer` 后的整串、32 位以上的长随机串。
- Rust 侧同规则，**纯字符串扫描实现**——不引入 regex 依赖（这工程刻意保持依赖少）。
- 两端都加单测；前端那条测的是**真正会进界面的路径**（`completeChat` 收到 401
  时构造出的 Error），不是只测工具函数。

过程中抓到一个**新引入的真 bug**：Rust 侧用字节索引切字符向量
（`chars[at..at+plen+1]` 与 `rest[..7]`），**中文错误原文会切在字符中间直接 panic**
（`end byte index 7 is not a char boundary`）。改成按字符切。

排障记录：第一版测试只测 `redactSecrets` 工具函数，去掉调用点它照样绿——
**测错了层**。补了走 `completeChat` 的路径级测试后，去掉调用点立刻失败。

### 来源矩阵：每类来源各测各的，整条线从没验过

产品主线是「多来源 → 收件箱 → 知识库 → 应用」。这条链上最容易出的问题是
**某个来源进了库却走不通**：进不了收件箱、搜不到、转不成卡、来源标签认不出。
此前每类来源各有各的冒烟，但**没有任何一套覆盖全部来源**——来源这条线是
**拼起来的，不是验过的**。

来源矩阵分两半，缺一不可：

**交互层**（`tools/source_matrix_smoke.mjs`，5 项，要真实浏览器）：

1. 进得了收件箱并带正确的来源标签
2. 能被搜索命中（索引要覆盖各自的正文与元数据）
3. 邮件还能按发件人搜到（索引覆盖 `from`）
4. 能转成知识卡，且卡片能回溯到原始素材（`materialId`）
5. 转卡后原始素材仍可回溯

**逻辑层**（`sourceMatrix.test.ts`，7 项，CI 每次都跑）：每种来源的搜索索引
（正文 / 发件人 / 文件名）、分类、来源标签。

分开是因为：浏览器冒烟在 CI 上跑不了（没有 `agent-browser`），直接把交互层
接进门禁会让 CI 直接红（`spawn agent-browser ENOENT`）。拆成两半后，
**逻辑层 CI 每次都跑，交互层本机跑**——而不是干脆从门禁里拿掉。

顺带修了一个真缺口：**手写笔记（`ink`）的来源标签显示成英文 `ink`**——
`Icon.tsx` 的 `META` 表里没登记它，而 `model.ts` 的分类是「手写笔记」，
同一件事两种说法。

写测试时也确认了两处**不是缺陷**的有意设计：

- 剪藏有 URL 时来源标签显示域名而非「网页剪藏」——按域名区分来源
  （GitHub / B站 / 公众号各有标签）是刻意的
- 来源标签文案以 `Icon.tsx` 的 `META` 表为准（文档 / 语音 / 随手灵感），
  `model.ts` 里那串是**分类**不是标签

已接进 `verify_workbench.sh`——它守的是整条来源线，不只是某一类。

### `.eml` 邮件文件根本导不进来

查「多来源」这条线时发现的真实缺口：**`.eml` 不在支持的导入格式里**。用户从邮箱
把邮件导出成文件后，导回知识库做不到——而「数据完全归你所有」是产品明写的承诺，
邮件显然是用户数据的一部分。

- 新增 `ui/workspace/emlParser.ts`：纯前端 `.eml` 解析，处理真实世界的复杂度：
  multipart 嵌套、base64 / quoted-printable 正文、字符集声明（按 `Content-Type`
  的 charset 解）、RFC 2047 编码的主题、附件文件名识别。
  **坏掉的邮件也要给出可用的结果**（至少给标题），不抛错。
- 导入流程新增 `.eml` 分支：产出 `sourceType="email"` 的素材，因此能进邮箱视图、
  参与来源洞察；按 `messageId` + 正文长度判重。

写测试时抓到两个**真 bug**（都是字节层处理错了）：

- RFC 2047 主题解出来是「229,173,163…」这样的**字节数字串**
- quoted-printable 正文解出来是乱码

根因：base64 与 quoted-printable 解出来的必须是**字节**，之前按字符处理了。
修法：base64 直接解字节；quoted-printable 的 `=XX` 是字节值，按 latin1 逐字节存，
再交给 `decodeBytes` 按邮件声明的字符集解读。

验证：单测 8 项、真实 `.eml` fixture（multipart + base64 + quoted-printable +
附件 + RFC 2047 主题）解析正确、端到端 3 条。

### 真实文件固化成仓库内 fixture（让方法可重复）

前三轮靠临时造真实文件抓到了三个缺陷（压缩 PDF 解析出源码、JPEG 被存成 .png、
订阅源相对链接点不开），但那些样本只躺在 `.scratch/` 里——下一轮就没了，
「用真实文件测」这个方法**无法重复执行**。

现在固化成仓库内的 fixture + 一套统一测试（`fixtures.test.ts`，11 项）：

`fixtures/` 下是**真实结构的文件**，不是能跑的理想样本：

| fixture | 特点 |
| --- | --- |
| `sample.pdf` / `sample-compressed.pdf` | 带 xref 与 `/Length`，后者是 FlateDecode（真实世界的 PDF 几乎都是压缩的） |
| `sample.docx` / `sample.pptx` | 真正的 ZIP 容器 |
| `sample.png` / `sample.jpg` / `sample.heic` | 真的文件头（测试里断言魔数，防止 fixture 本身造错） |
| `sample-rss.xml` / `sample-atom.xml` | CDATA、HTML 实体、各种日期格式、相对链接、缺链接的坏条目 |
| `sample-page.html` / `sample-page-gbk.html` | UTF-8 与 GBK 两种编码 |

字节以 base64 存进 `bytes.json`（`?raw` 导入后解码）。不用 `?url`+fetch 是因为
vitest 里拿不到 dev server 资源；不用 `?raw` 直接导入二进制是因为 raw 会把
二进制当 UTF-8 处理、字节会坏。

**反向验证过**：把 PDF 解压分支与相对链接补全分别关掉，这套测试立刻失败两条
——它确实守得住，不只是装饰。

### 剪藏到知识卡：这条转换链此前完全没有覆盖

造了真实结构的页面（GBK / GB2312 / UTF-8 / BOM / `http-equiv` 声明 /
`og:title` / `base href` / 相对链接）跑一遍——**剪藏这块质量很高，全部处理正确**：

- GB2312、GBK 页面中文都不乱码；带 BOM 的页面正常
- `http-equiv="Content-Type"` 声明 charset 能识别
- 只有 `og:title` 没有 `title` 时能取到
- `base href` 的相对链接能补全

三处 charset 实现（Kotlin / TypeScript / Rust）的一致性由
`tools/check_clip_parity.py` 守着，已跑通。

顺手把「剪藏 → 知识卡」这条转换链的断言补上——它是「来源」到「知识库」的转换，
也是整条回溯链的起点：

- 剪藏素材转成知识卡；卡片带回「原始来源」链接
- 素材标记为已处理（离开收件箱）；**原始素材仍可回溯**（没被转走就删掉）
- 同一素材重复转、甚至连点两次，都不会多出一张卡
  （去重靠 cards state，靠 `act()` 的 busy 守卫挡住连点）

### 订阅源里的相对链接点开是无效地址

真实 feed 里的文章链接常是相对的（`/posts/2`），解析器原样存成素材的「原文链接」，
用户点开会指向无效地址。

- `parseFeed` 加 `baseUrl` 参数：相对链接用 feed 自身的 origin 补全
  （`/posts/2` → `https://example.com/posts/2`）；协议相对（`//host/x`）也处理。
- `parseSubscriptionPayload` 把 `sub.targetUrl` 传下去。
- **没有 base 时不乱补**，相对链接原样保留（不猜）。

单测 4 项，fixture 是**真实结构的 feed**（不是理想样本）：

- 真实 RSS：CDATA、HTML 实体、`content:encoded` 优先于 `description`、
  RFC822 与 ISO 两种日期格式、缺链接的坏条目要跳过而不是让整次抓取作废。
- 真实 Atom：`entry`、`type=html` 的 `summary`、转义标题、`urn:uuid` 作 key。

### 浏览器不给 MIME 时，JPEG 被存成 .png

查「真实图片导入」时抓到的缺陷：图片导入的 mime 完全依赖浏览器的 `File.type`，
而 **File.type 不是总有的**（HEIC 尤其常见，部分系统对 JPEG 也给空）。给空时
代码一律当成 `image/png`——于是 **JPEG 被存成 `.png`、HEIC 也被存成 `.png`**。
落盘时扩展名由 mime 决定，所以文件内容与扩展名不符，有些查看器直接打不开。

- 新增 `domain/mediaMime.ts`：扩展名 → MIME 的**单一映射**，导入与恢复共用。
  落盘时扩展名由 MIME 决定、恢复时又要由扩展名反推 MIME，两处必须同一份映射，
  否则会出现「内容是 JPEG、文件叫 .png」的错位。
- `imageMimeOf`：扩展名优先，其次才信 `File.type`（扩展名更接近「文件本来是什么」）。
- 恢复路径改用同一份映射，顺带补上漏掉的 `heif`。

验证：

- 单测 6 项：浏览器不给 MIME 时按扩展名推断、扩展名优先于浏览器给的类型、
  都不认识时兜底 PNG、大写扩展名也认、恢复时反查 MIME 不认识就 `undefined`。
- 端到端 1 项：真实浏览器里用 `type` 为空的 File 导入 `.jpg` 与 `.heic`，
  断言落库的 mime 分别是 `image/jpeg` 与 `image/heic`。

### 压缩 PDF 解析出的是 PDF 源码，不是文档内容

用户点名过 pdf / word / ppt 是来源之一，但此前的导入验证全用笔记类文本文件，
**真实文档解析路径从没验过**。造了真实结构的文件（带 xref、/Length、ZIP 容器）跑
一遍，立刻抓到一个真实缺陷：

> **真实世界的 PDF 几乎都用 FlateDecode 压缩内容流。** 解析器不解压的话，抽出来的
> 不是文档内容，而是 PDF 源码本身——`1.4 1 0 obj Type Catalog Pages 2 0 R endobj…`。
> 用户导入绝大多数 PDF 会得到一堆乱码，而导入流程看起来「成功了」。

修法两处：

1. **按字节定位流**，不再用正则截取。流里有任意字节，正则的 `\r?\n` 会把流内的
   换行吃掉，解压就报 `incorrect header check`。改成读对象头里声明的 `/Length`
   精确取字节；`/Length` 不可信时（有些生成器写错）退回按 `endstream` 截取。
2. **解压 FlateDecode 流**（zlib 格式，用已有的 `decompressDeflateRaw` 助手）。

验证：

- 单测 1 项：fixture 是一份真实结构的压缩 PDF（base64 内嵌），断言正文是
  `KnowFlick Compressed PDF`，且**不含** `obj` / `endstream` 这类源码特征。
- **反向验证过**：把解压分支关掉，这条测试立刻失败——它确实钉得住这个缺陷。
- 真实浏览器里走完整导入路径（构造 File → 塞进导入 input → change 事件），
  压缩 PDF 的 `rawText` 已是正确正文。
- 真实 DOCX / PPTX 解析结果一并复验：标题层级、每页内容都正确。

### 复习闭环此前只验到「记过一次」，没验「下次什么时候复习」

复习冒烟此前只验到「评分写回卡片」。但复习的核心不是「记过一次」，而是
**下次该什么时候复习被算出来并存住**。补 10 条断言把这三段钉住：

- 评分后算出间隔并写回（`intervalDays > 0`、`lastReviewedAt` 非空）
- 掌握度 / 重复次数前进
- **重载后间隔仍在**——只存在内存里等于没复习过
- 评为「重来」会清零重复次数与掌握度、间隔压回 1 天
- 统计里的平均间隔按新间隔更新；未来 7 天到期负荷可见、今天不再有待复习的卡

途中核实了一件事：**「良好」首次间隔是 3 天、「较难」是 1 天**——查了 SM2 与 FSRS
两套算法（`newRepetition === 1` 时 hard→1；FSRS `INITIAL_S[1]=1.2`），都是标准
行为，不是缺陷，所以没动算法。

排障记录：一度以为「复习过的卡没移出到期队列」是 bug，实测页面显示
「本轮温故复习完成…未来 7 天到期负荷：10-24 有 1 张」——行为完全正确，
是我断言写错了（完成提示会一直显示，不是「今天没有到期的卡片」）。

### 恢复备份时静默丢弃空标题/空正文的内容

「数据完全归你所有」是设置页写着的承诺。查这条承诺的往返时发现恢复会丢内容：
恢复逻辑用 `if (!c.headline || !c.details) continue` 与 `|| !m.title` 过滤，
于是**标题或正文为空**的卡片、**标题为空**的素材在恢复时被静默丢弃——
备份里明明写进去了，恢复回来却少了内容。

改法：只挡真正无法入库的行（没有 id、正文不是字符串）。标题/正文为空不代表这条
记录无效，那是用户自己建的（空标题的笔记、只有标题的卡片都很常见）。

**反向验证过**：把过滤改回原样，端到端断言立刻失败——这条测试确实钉得住它。

- 端到端 3 条走真实 `.kfbackup` 链路：造边界样本 → 点导出按钮拿字节 → 清库 →
  走真实恢复输入框 → 断言三类边界内容都回来了。
- 单测 1 项：带边角取值的卡片与素材逐字段无损往返（空串、0 时间戳、null、
  含制表与引号的正文、`dismissed` 状态）。

### 搜索无结果：文案承诺了动作，界面上做不到

入口**——用户得自己回到搜索框手动删词，还得记得把标签也点掉。

### 跨端导入丢精度：复习间隔被悄悄改写

上轮只修了**导出侧**（`cards.json` 导出空数组）。这轮做**导入侧**——用工作台真实
导出的字节喂给安卓解析器，结果抓到一个会让复习进度被改写的缺陷。

已有测试都只测「安卓端自己读了再写」，从没测过**对端真实产出**。新测试的 fixture
就是 `read_cards_json_text` 打印出来的真实输出。

**失败项就是缺陷**：桌面端 `intervalDays` 是 `f64`，导出 `0.0`；安卓端 `intField`
只认 `intOrNull`，读成 null 后被 `?: 1` 兜底成 **1 天**——两端搬一次卡，复习间隔
就被悄无声息改了，正好违反 ADR-0002 §3「到期不变」。

修 `CardJson.intField`：按原文解析 double 再取整（这个 kotlinx 版本没有
`doubleOrNull`）。

**另一处已知差距**：桌面端卡片有 `tags`，安卓端的 `KnowledgeCard` 没有这个字段、
`CardJson` 也不处理——桌面端打的标签导出到安卓会静默丢失。这条记在这里，
没有在两端之间强行加字段（那会改动安卓的数据模型与界面，超出本轮范围）。

### 归档素材被当成「讨厌这个来源」，悄悄污染偏好

查归档路径时发现一处语义错配：

- 工作台阅读区的「归档素材」把状态写成 `dismissed`（已忽略），
  提示却写「素材已归档，可在已归档中找回」——**状态与文案自相矛盾**。
- 更实质的问题：来源洞察把 `dismissed` 当作**用户明确忽略**的负面信号并给该来源
  降权。于是用户只是归档了一份不再需要的邮件，这个发件人的权重就被降了——
  **他并没有表示讨厌这个来源**。这类错误偏好会随使用不断累积。

改法：归档写 `processed`（处理完了），`dismissed` 只留给「明确忽略」这个动作。
邮箱页的「忽略」语义不变（那里确实是用户表达不要）。

单测锁住语义分离：归档不降权、明确忽略才降权。

### 桌面端不能导出 Anki 词表（安卓端一直可以）

扫「命令在、界面没有」的断裂时确认所有 Rust 命令都被调用了（上轮那类问题已清干净），
于是换个方向**比两端能力**，发现一处真实差距：**Android 端能导出 Anki TSV，桌面端不能**。

Anki 是最常用的外部复习工具，「把卡带到别的工具里继续刷」正是知识库做应用该有的出口。

- 桌面端新增 `exportAnkiTsv` / `downloadAnkiTsv`，格式与 Android 端
  `CardExportEngine.exportAnkiTSv` **逐字段一致**（front / back / category）。
- 设置页新增「导出 Anki 词表 (.tsv)」入口（纯文本，浏览器里也能下载）。
- 写测试时抓到**两端共有的缺陷**：背面只替换了制表符、**没替换换行**，
  多行正文会把 TSV 撑成多行、Anki 导入就错位。桌面端修好后，Android 端同步修复
  ——否则两端产出的文件不一致，那才是真问题。

### 跨端契约 `cards.json` 实际是断的

扫未引用符号时本来打算清死代码，查文档发现 `save_cards` / `export_archive` 在
CHANGELOG 与文档里被提到，是 ADR-0002 §3 的跨端契约，**不能删**。顺着查下去
发现了真问题。

[ADR-0002 §3](../../docs/adr/0002-desktop-web-split-from-android.md) 承诺：「两套共享
同一份 `cards.json`、拷过去就能打开，中间不经转换」。

| 事实 | 后果 |
| --- | --- |
| Android 端仍在用 `cards.json`（原子写 + 备份轮转），导入也支持 | 契约在安卓侧是活的 |
| 工作台早已把卡片搬进 SQLite，**不再写那个文件** | 契约在桌面侧断了 |
| `export_cards_json` 只读磁盘上的 `cards.json`，而该文件不存在（库里只有 `knowflick.db`） | **导出的永远是 `[]`** |
| 命令在 bridge 里存在，**界面上没有任何入口** | 用户根本拿不到这份文件 |

**这条契约断了两层**：读不到数据 + 没有出口。

修法：

- 新增 `read_cards_json_text`：优先从 SQLite 导出与安卓同格式的裸数组；库里没有
  卡片时退回旧 `cards.json`（未迁移的库仍能导出）。`export_archive` 同源。
- 设置页「数据主权与开放导出」新增「导出 cards.json（给安卓用）」；桌面端可导出，
  浏览器体验没有本地文件系统，改为**说明原因**而不是让按钮凭空消失。
- 导出后回执指明用途：「把它放到安卓端的数据目录即可打开」。

Rust 单测锁住契约：SQLite 里的卡能被导出且是裸数组线格式；未迁移的库仍能从旧
`cards.json` 导出。

**教训**：扫「未引用符号」本来是要清死代码的，结果查文档才发现它们是活的契约。
删之前先查文档与历史——「没人调用」不等于「该删」。

### 「统计」是 ADR 承诺过、命令早就在的功能，界面却没有

[ADR-0002](../../docs/adr/0002-desktop-web-split-from-android.md) 把「统计」列进第一版
交付物：「剪藏、笔记导入、AI 出卡、刷卡、卡库与详情、收藏与历史、测验、**统计**、导出」。
Rust 侧的 `db_get_stats` 也早就实现并注册好了——但前端从未调用，界面上也没有入口。

  每个指标都写清含义，不只给数字。
- 桌面端走 SQLite 的 `db_get_stats`；浏览器体验没有这层表，用前端内存算同样的指标
  （含到期判定，与 Rust 侧同一套间隔规则），两边口径一致。

### 「笔记转知识卡」解析器早就写好，却没有入口

`parseNotesFile` 是个完整功能——把 Markdown/JSON 笔记拆成可复习的原子卡（支持
frontmatter、分段、代码块），却**从来没有入口**。「把攒下的笔记直接变成能复习的卡」
是笔记软件最该有的能力。

- 「记录」下新增「笔记」入口：选 `.md/.txt/.json` 直接转成知识卡。
  与「导入文件」分开——后者把文件收进收件箱当素材，这里直接变成可复习的卡。
- 顺带修 `parseNotesFile` 的两个真实缺陷：
  1. **frontmatter 里的 tags 被静默丢弃**——写了却不生效。
  2. 拆成多张卡时，**文件级 frontmatter 的分类与标签只落在第一张**，其余全丢；
     同一篇笔记拆出来的卡本该同类。现在文件级元数据传给每张。

新增「笔记转卡」的 input 打乱了依赖 DOM 顺序的冒烟选择器——导入冒烟因此把文件

### 操作音效开关：只存不用，且没有入口

扫「导出但从未被引用」的符号时发现 `playSwipeTone` / `playPaperSlide` 一次都没被

### 批量栏缺「导出选中」

批量操作只有「打标 / 收藏 / 设分类 / 归档」，想把挑出来的几条带走只能全库导出

- 批量栏新增「导出选中」：素材与卡片都支持，复用整库导出的同一套生成逻辑

- 单测锁住语义：只导出传入的条目、选中为空产出空集。
  **不能退化成导出全库**——否则用户以为只导了几条，实际把整个库带走了。

### 规模：4000 条内容下交互仍然跟得上（以及一次测量陷阱）

查「几千条后交互还跟不跟得上」时，我先用 `Date.now()` 包住一次 `agent-browser`
调用，得到「筛选 286ms、搜索 290ms」——看起来该优化了。

但实测**空 eval 往返就是 166ms**：这些数字里大半是 CLI 进程启动开销，不是界面开销。
改用**页内 `performance.now()`** 测量同步阻塞，真实结果：

| 指标 | 4000 条内容（2000 素材 + 2000 卡） |
| --- | --- |
| 打开到可交互 | 约 225ms（已扣除 CLI 开销） |
| 首屏渲染行数 | 60 行（分页上限，受控） |
| 逐字输入最慢 | **61ms**（预算 150ms） |
| 搜索命中 | 正常 |
| 清空搜索恢复分页 | 正常 |

**结论：没有性能问题，不需要优化。**

已固化为 `tools/scale_ui_smoke.mjs`（6 项）。测试里写明了为什么要页内计时——
"测量方法错了"与真正的性能退化在数据上长得一样，后者才是需要优化的。

### 产物看不到依据哪几张卡

产物库只显示「依据 N 张卡片」，看不到是哪几张、也点不进去。回溯链断在最后一跳
——而「检索命中的卡片可直接定位回溯」是这个产品写在界面上的承诺。

- 产物条目下列出依据卡片（标题可点），点击跳到知识库并选中那张卡。
- 卡片已被删除时标为「（已删除的卡片）」且不可点，与问答引用的处理保持一致
  ——不给一个看起来能点、点了会静默跳错的按钮。
- 产物页接收当前卡片库，用 id 解析标题，**不存快照**。

### 已保存的产物对问答不可见

问答的检索一直只覆盖知识卡。产物库（认知简报等）存的是**用户自己沉淀的结论**，
但对问答完全不可见——存下来等于只给备份看。

- 问答接收 artifacts：按关键词命中标题或正文，最多取 2 份进上下文。
- 桌面端 Prompt 增加「已保存的产物（用户自己沉淀的结论）」段落，与卡片参考并列；
  浏览器演示模式也会列出命中的产物。
- 产物状态提到 Workspace 统一加载：产物库与问答共用同一份数据。
- 检索为空的条件改为「卡片与产物都没有」，只有卡片为空不再直接返回。

**排障记录**：这条断言一开始失败，不是功能问题——未配密钥时第一次提交会被守卫
拦下（上一轮故意如此），而测试只点了一次。改成走完整的两次点击后通过。
这类"测试自己没走完流程"造成的假红，与功能坏了看起来一样，必须靠读代码路径区分。

### 订阅素材能筛出来，却仍然只能一条条点

上一轮让订阅来源可识别、可筛选，但筛出来之后没有下一步：批量栏只认知识卡
（`batchCards`），选中的素材连按钮都不出现。订阅会持续进货，「只筛不整理」
等于没解决问题。

- 批量栏按选中内容的类型分支：选素材显示「已选 N 条素材」+ **归档**；
  选卡片才显示标记已复习 / 收藏 / 设分类。
- 素材**不提供硬删除**：归档（`processed`）已经是"处理过了"的语义，删掉原始记录
  等于把知识卡的回溯链断掉。
- 归档只处理仍为 `inbox` 的素材，已处理的不重复写；完成后收起批量栏并回执。

回归补 5 条，其中**状态断言比按钮存在断言更重要**：

| 断言 | 为什么 |
| --- | --- |
| 多选订阅素材出现批量栏 | 入口在不在 |
| 出现归档入口 | 动作在不在 |
| **归档真的改了状态**（比对 inbox 条数前后） | 按钮出现但点了不生效，是这类"看起来能用"最容易漏的情况 |
| 有回执 | 用户知不知道发生了什么 |
| 归档后批量栏收起 | 状态有没有收敛 |

### 订阅来源在收件箱里认不出来

订阅源会持续把内容收进收件箱，但这些素材在列表里只显示**域名**——和手动剪藏的
网页长得一模一样。用户既分不清「哪些是订阅自动收的」，也没法把这一批单独拎出来
清理。来源在这里只是入口，不是可用维度。

- `sourceLabel` 接受 `subscriptionId`：来自订阅的素材标为「订阅」而不是域名。
  订阅抓的是网页，只看 `sourceType` 与域名叫不出真实来源。
- 新增 `subscriptionIdOf`：从 `metadataJson` 读订阅 id，坏元数据返回 `null`
  而不是让整条素材消失。
- 筛选栏增加「订阅」：订阅不是内容类型而是来源属性，所以按 kind 之外的维度过滤；
  知识卡不会被误留。

**一个自我纠正**：探针里读侧栏第一个 `.ws-count` 得到「收件箱 0」，实际那是邮箱的
计数——精确取值后是「收件箱 3」，与列表一致。计数逻辑没有缺陷，是探针读错了。
写进文档是因为这类"看错自己量到的东西"比 bug 更容易误导后续判断。

### 产物库存进去却读不到

简报有「存入产物库」，但产物只在简报页内部读一次就丢掉，**界面上没有任何入口**
——存进去的生成物只有导出备份时才看得见。等于一个只写不读的抽屉。

- 新增「产物库」页（应用段，与知识问答、认知简报并列）：列出标题、日期、依据
  卡片数；可展开读全文、复制 Markdown、删除。空态明确指路「去生成简报」。
- 补上产物删除能力：shell 桥与 Rust 命令原本都没有。按表里已有的 `is_deleted`
  做**软删除**——硬删会让「依据这 N 张卡片生成的简报」凭空消失。
- Rust 单测锁住软删除语义：列表不再出现、行仍在、再存一次能复活。

### 问答引用指向已删除的卡片时静默跳错

上一轮把对话持久化了，这轮顺着查引用：卡片被删除后，持久化里的引用仍指向那个
id，点下去会**静默跳到另一张卡片**——比报错更糟，用户以为看到的是那张
被引用的卡。

- 引用不再整张卡入库，只存 `{ id, headline }`；渲染时按**当前卡片库**解析。
- 卡片不存在就显示「（已删除）」并禁用点击（虚线删除线），不再是一个看起来
  能点的按钮。
- 标题取当前卡片库里的（卡片可能被改过标题），存的那份只作兜底——
  实测卡片改名后引用显示的是新标题，符合「引用指向当前那张卡」的预期。
- 兼容旧格式：旧版本存的是整张卡片对象，读取时照样取出 id/headline，
  **升级不该让用户的历史引用消失**。

### 简报「重新分析」看起来像没反应

它是纯本地重算（不依赖模型），但卡片没变时结果完全一样。现在按下后按钮文案
短暂变为「已按当前卡片重算」。

### 未配密钥时提问「点了没反应」

守卫写成 `needsKey && inShell()`——只在桌面端拦截。浏览器模式下即使明知没有
密钥，也会发出一个注定失败的请求，界面要转到 **120 秒超时**才报错。

现在两种模式都先拦一次并说明「若服务端不需要密钥，再点一次即可继续」，
确认后不再重复拦截。既不让人干等，也不封死自建的无密钥服务端。

同时补上「应用」阶段的第一条自动化覆盖：`brain_ui_smoke`（36 项），
覆盖问答的密钥守卫与二次确认、**对话的切页/刷新持久化与清空**、
**引用指向已删除卡片时的表现与旧格式兼容**、
**产物库的列出/展开/删除**、简报的结构化板块、可执行动作与重新分析的反馈。

## 七·补·旧：应用阶段的批量操作

产品要求里写过「对知识做应用做总结做一系列操作」，但列表一直是**单选**：
点谁选谁，整理几十张卡只能一张张点。这是应用阶段最大的缺口。

- ⌘/Ctrl（Shift 也接受）点击追加或取消；普通点击仍是单选并**退出多选**，
  不留下看不见的待处理选择。
- 换页 / 换筛选自动清空选择：旧选择多半已经不可见，留着容易误操作。
- 多选知识卡时列表顶部出现批量栏：**标记已复习 / 收藏 / 设统一分类** + 退出。
  三个操作都写回全部选中卡片，并回执「已处理 N 张卡片」。
- **批量栏只对卡片开放**：素材是原始记录，归档走收件箱语义，
  不在这里批量处理——避免给一个「批量删素材」的假入口。
- 被勾选的行有可见标记（左侧强调色竖条 + 淡底），不只靠颜色区分。

回归里踩到两件事：

1. **两次 ⌘ 点击连着 dispatch 会打到同一批旧节点**——选中态变化会让列表重渲染。
   改成两次独立点击（间隔 350ms），这也更接近真实操作序列。
2. **带条件的断言等于没有断言**：卡片数不足 2 时整段批量断言永远不执行、
   也不报错，通过时一声不吭。改成先补足第二张卡再断言，保证断言真的会跑。

## 八·补：备份带走附件后的三个连带修复

- **只有素材的旧备份不再被标成失败**：`knowflick-workspace` 分支先落库素材，
  又要求 `cards` 必须是数组，于是同一份文件既报「已导入 N 条」又报「以下文件没有导入」。
- **附件报错中文化**：`media.rs` 暴露给用户的 10 条错误原是英文（路径无效、附件过大、
  写入不完整…），一律改成中文。
- **图片上限前后端对齐**：前端允许 32 MB、后端只收 16 MB，20 MB 的图会一路走到写入阶段
  才收到英文报错；现在导入时先按 16 MB 拦截并用中文说明。
- **库目录透传 + 附件缺失提示**：`saveMedia`/`readMedia` 原先写死 `dir: null`，
  自定义库目录时会写到默认库；现在与其它 shell 调用一致。读取失败不再静默留白。

## 九、一条验证纪律（CI 教会的）

有一轮我用 `grep -E "Test Files|..." ./tools/verify_workbench.sh` 来读结果，
**没看退出码**：`set -e` 下 `tsc` 失败会中止脚本，但 grep 仍会打印前面匹配到的行，
看起来像全绿。结果提交后 CI 的 `tsc` 步骤报 `TS18048`，本地却一路"通过"。

**门禁一律这样跑**：

```sh
./tools/verify_workbench.sh > /tmp/verify.log 2>&1; code=$?; echo "exit=$code"; ...
```

grep 只用来读摘要，判断"是否通过"必须看 `exit=`。

## 十、实测后判定**不用动**的地方

避免拍脑袋优化，这两处是量过才下的结论：

| 项目 | 实测 | 结论 |
| --- | --- | --- |
| 长列表性能 | 200 / 1000 / 3000 条，打开到可交互分别 ~408 / ~366 / ~443 ms | 不做虚拟化 |
| 列表分页 | 首屏固定 60 行，「加载更多（还有 N 条）」可用，点一次 60 → 120 | 已够用 |

列表本来就有 `visibleCount` 分页，不是静默截断——这条也进了门禁断言
（只有真被截断时才要求出现「加载更多」）。

## 十一、边界

1. **去重是精确匹配**，不是模糊相似度：改一个字就是新内容。想合并相近内容得靠后续的整理功能。
2. **图片不参与全文检索**：没有 OCR，图片素材按标题与文件名可搜。
3. **120 秒超时对长报告可能偏短**：超时后已保存内容不受影响，但需要重试。
4. **首屏 60 行是写死的**，没有按窗口高度自适应。
5. 真机（Tauri）里只确认了界面与命令存在，**录音与图片附件的真机链路尚未逐步点过**。
