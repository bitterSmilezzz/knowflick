# 第二阶段第二十三刀：自动同步的定时器迁到 Go

> 承接 ADR-0031。SyncDue 是「跑一轮」，这一批加定时器让它持续跑。

## 一、迁了什么

| 能力 | Go | 位置 |
| --- | --- | --- |
| 定时器 | Loop | mailschedule：立即跑第一次，之后按间隔重复，ctx 取消即停 |
| 与同步接线 | SyncDueLoop | mailrunner：每轮重新查库再跑 SyncDue |
| 单轮失败不终止 | Loop | step 报错交给 onError，下一轮照常尝试 |

## 二、与 Rust 的一处架构差异（必须说清）

Rust 的后端**没有**定时器：它由界面每 60 秒调一次 mail_sync_due_accounts
（Workspace.tsx 的 window.setInterval(..., 60_000)，shell 的 mailSyncDueAccounts）。

Go 把定时器放在后端（mailschedule.Loop）。

这是**放置位置的差异，不是规则差异**：判定「谁该同步」的规则仍是同一个
（interval 为 0 关闭、按尝试时间算间隔），只是「谁来掐表」从界面挪到了进程内。

为什么这么放：后端持有锁与库连接，进程内定时不需要界面在线；代价是与 Rust 的行为
不再逐字相同，所以这条记在这里而不是含糊过去。

## 三、每轮重新查库

SyncDueLoop 每轮都重新调用 SyncDue（内部重新 LoadAccounts），不缓存账号列表。

原因：用户在两次轮询之间可能改了同步间隔或删了账号。缓存会让「刚关掉的账号还在跑」。

## 四、验证

| 用例 | 内容 |
| --- | --- |
| Go 4 项（Loop） | 立即跑第一次再按 tick 重复；step 报错不终止循环且错误被上报；间隔 <= 0 被拒；取消后不再跑 |
| Go 1 项（SyncDueLoop） | 真实链路：第一轮连本地假 IMAP 导入 1 封，后续轮次因间隔跳过；断言轮数 >= 2 且素材仍为 1（不重复导入） |
| 未做跨运行时对拍 | Rust 没有后端定时器（见第二节），没有可对拍的对象；到期判定已在 ADR-0029/0031 对拍过 |

### 4.1 测试里踩到的两处

1. **假服务器只接受一次连接**：第二轮连不上，挂在 TLS 握手直到 15 秒超时。
   改成 accept 循环 + 每连接一个 goroutine。
2. **让时钟每调用一次推进 10 分钟会越过会话预算**：imap 的会话预算是 120 秒，
   时钟一跳 10 分钟就被判「连接时间太长」。改成固定时钟——第一轮到期并导入，
   之后 last_attempt_at 等于当前时刻、按间隔跳过。这反而同时验证了「不重复导入」。

## 五、还没做

| 项 | 现状 |
| --- | --- |
| 启动挂载 | 未做。没有地方在应用启动时调用 SyncDueLoop |
| 界面入口 | 未做。Go 预览界面没有邮箱入口 |
| 真实邮箱 | **未验** |
| 备份包里的邮箱数据 | 未迁 |

**Go 版现在有可用的定时器，但没人启动它**——缺一个在应用启动时挂载的位置。
