# 第二阶段第二十一刀：调度循环迁到 Go

> 承接 ADR-0029。`Due` 能回答「谁该跑」，这一批把它变成「跑一轮到期账号」。

## 一、迁了什么

| 能力 | Go | 与 Rust 的关系 |
| --- | --- | --- |
| 一轮调度 | RunDue | 对应 `sync_due_using`：判定到期 → 逐个同步 → 收集结果 |
| 串行执行 | RunDue | 每个账号都要动游标，并发会互相覆盖进度 |
| 单账号失败不阻断 | RunDue | 密码错了不该让别的账号也停 |
| 取消 | RunDue | ctx 取消时立刻停，不把已开始的结果丢掉 |

`Syncer` 接口让调度循环不关心「怎么同步」——测试用假实现，生产接 mailrunner。

## 二、为什么串行而不是并发

每个账号的同步都要读游标、推进、提交。并发时两方会互相覆盖进度，表现为「同步跑完了但游标没动」。

Rust 用 `ACCOUNT_LOCK` 全局串行化；Go 在调度层就串行，省掉锁的竞争。

## 三、验证

| 用例 | 内容 |
| --- | --- |
| Go 3 项 | 只同步到期账号（关闭与间隔内的不跑）；一个账号失败不阻断其余；取消时不跑任何账号 |
| 跨运行时对拍 | Rust `go_mail_loop_parity` 比对一轮调度的结果：只选中 `due`，导入 4、拒收 1，**逐项一致** |

## 四、还没做

| 项 | 现状 |
| --- | --- |
| 定时器 | 未做。`RunDue` 是「跑一轮」，没人按分钟调用它 |
| 与 mailrunner 接线 | 未接。`Syncer` 接口已定义，生产实现还没写 |
| 界面入口 | 未做 |
| 真实邮箱 | 未验 |

**Go 版现在能跑一轮到期账号，但还没有定时器，也还没接到真实同步上。**

## 五、下一步

写一个 `Syncer` 实现把 `RunDue` 接到 `mailrunner`，再加一个定时器按分钟调用它。
