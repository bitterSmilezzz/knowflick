# 第二阶段第十三刀：IMAP 的 TLS 连接与 UID 搜索取信迁到 Go

> 承接 ADR-0021 的协议层。这一批补上两块，Go 侧因此能**真正连服务器并取到邮件正文**。

## 一、迁了什么

| 能力 | Go | 与 Rust 的关系 |
| --- | --- | --- |
| TLS 连接 | Connect | TLS 1.2 起、系统根、主机名校验；DNS 解析带 15 秒超时；最多 8 个地址逐个尝试，每个用剩余预算 |
| UID 搜索 | SearchRange | `UID SEARCH UID after+1:*`；结果始终**升序**；newestFirst 保留最新 N 封；丢弃 `<= after` 的 UID |
| 取信 | Fetch | 先查 RFC822.SIZE，超限返回「不能导入」而不是让整轮失败；正文用 `BODY.PEEK[]` 请求 |

## 二、三条容易做错的语义

### 2.1 列表升序，即使取的是「最新 N 封」

首同步要「最近 N 封」，但返回的列表**仍然升序**。原因是调用方按行推进游标：降序会让游标倒退，失败时较新的 UID 会漏重试。

### 2.2 响应里是 BODY[]，不是 BODY.PEEK[]

RFC 3501 回显的是**被请求的段**，PEEK 只是请求修饰符，服务器不回显它。
Rust 的注释记着：早期要求响应里必须有 `BODY.PEEK[]`，结果真实导入全部失败。Go 侧照抄这个教训——请求写 PEEK，断言只认 `BODY[`。

### 2.3 `100:*` 会返回末号本身

当 100 超过邮箱末号时，`UID SEARCH UID 100:*` 仍返回末号。那个 UID 并不比游标新，必须按 `uid > after` 过滤，否则每次同步都会重试同一封。

## 三、验证

| 用例 | 内容 |
| --- | --- |
| Go 12 项 | 升序与边界（含 `<= after` 丢弃）；newestFirst 保留 4,5；缺 SEARCH 字段报错；through<=after 短路；超限邮件返回「不能导入」；正文返回且接受 `BODY[]`；UID 不匹配报错；token 解析；**自签名证书被拒**（TLS 校验真的生效）；不可解析主机与关闭端口被拒 |
| 跨运行时对拍 | Rust `go_imap_uid_parity` 比对同一组响应下的 `search_all=11,12,13,200`、`search_newest2=4,5`、`fetch_body=hello`，**逐项一致** |

### 3.1 一个测试教训

TLS 校验那条测试我一开始手写了一段 PEM 常量，结果 `x509: malformed algorithm identifier`——base64 内容是我编的。改成用 `x509.CreateCertificate` 现场生成自签名证书，测试才真正有意义。

**手写证书常量是在自欺**：它看起来像在测 TLS，实际测的是「我抄的字符串能不能解析」。
