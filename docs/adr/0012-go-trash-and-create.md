# 第二阶段第三刀：新建笔记与回收站恢复

> 承接 [ADR-0011](0011-go-editor-ui.md)。那一轮能编辑、能删；这一轮补上「能创建、能后悔」。

## 一、做了什么

| 能力 | 后端 | 前端 |
| --- | --- | --- |
| 新建笔记 | `Upsert` 的 `baseRevision=0` 分支 | 「新建笔记」按钮，`crypto.randomUUID()` 生成 id，空标题空正文 |
| 回收站列表 | `Library.ListDeleted`（`is_deleted=1`，按删除时间倒序） | 「回收站 / 返回笔记」切换 |
| 恢复 | `Library.Restore`，与 Rust `note_restore` 同义：清删除态、`deleted_at=NULL`、重进 FTS、按当前修订重建分块 | 回收站里每篇一个「恢复」按钮 |

恢复里最容易被漏掉的是**分块重建**：只把 `is_deleted` 改回 0 的话，笔记在列表里出现了，但分块检索仍然是瞎的。`Restore` 与 Rust 一样把这件事放在同一个事务里。

## 二、原生窗口实测（夹具副本）

| 步骤 | 界面 | 数据库 |
| --- | --- | --- |
| 初始 | 已显示 1 篇；「回收站」按钮可见 | 1 篇活动 + 1 篇已删 |
| 进回收站 | 「已显示 1 篇」＋「第二篇」＋「恢复」按钮 | `is_deleted=1` |
| 点恢复 | 回执「已恢复到笔记列表」，**已显示 2 篇**，含「第二篇」 | `is_deleted=0`、`deleted_at=NULL`、`fts_notes` 对应行 1、分块按修订 1 重建 |
| 新建笔记 | 回执「已新建笔记」，**已显示 3 篇** | 新增一行「无标题笔记」，总数 3 |

### 一个过程 bug（已修并复验）

首版恢复后界面仍显示「已显示 0 篇」，但数据库里已经恢复成功——`reload()` 读的是闭包里的旧 `trash=true`，把刚恢复的笔记又按回收站查了一遍。修法是给 `reload` 加显式 `trashMode` 参数，恢复与新建都传 `false`。**修后复验为「已显示 2 篇」**。

这类 bug 的教训：状态切换后的「刷新」不能隐式复用旧状态，否则界面会自信地显示一个和数据库相反的结果。
