# 第二阶段第二十七刀：备份包端到端加密（e2ee）迁到 Go

> R3 第 3 项，LOCAL_DATA_AND_AI「可选 E2EE」。这是本轮迁移里**唯一对字节级兼容性有硬要求**的模块：
> 一边加密、另一边必须能解开，否则用户升级换端后备份就打不开了。

## 一、迁了什么

| 能力 | Go | 与 Rust 的关系 |
| --- | --- | --- |
| 派生密钥 | deriveKey | SHA256(salt) 起步，迭代轮 key=SHA256(key||pass||i_le_u32)，每轮混入轮次号 |
| 加密 | Encrypt | AES-256-GCM；容器 = 头(8) + 轮数(u32 LE) + 盐(16) + nonce(12) + 密文 |
| 解密 | Decrypt | 魔数只比前 6 字节；版本位在 offset 6，不认识就明确报错 |
| 轮数 | DefaultIterations = 210_000 | OWASP 2023 对 SHA-256 的建议值，且**写进密文头**，未来可调、旧文件仍能解 |

## 二、三条设计取舍（照抄原实现）

### 2.1 版本位不进魔数

魔数只比 `KFENC\0` 六字节，[6] 才是版本。否则将来版本 2 的文件会被报成「不是加密文件」，
用户看到的是「文件坏了」而不是「请用更新版本打开」——两种诊断的修法完全不同。

### 2.2 认证加密，密文被改要失败

AES-256-GCM 在服务端篡改一个字节时解密直接失败，错误与「口令不对」同一条。
绝不能静默还原出坏数据：坏数据进备份比打不开危险得多。

### 2.3 忘记口令不能找回，错误消息如实说

原文：「口令不对，或文件在服务端被改动（认证校验没过）。忘记口令无法找回——这是端到端加密的代价」。
不给「重置口令」这种假希望。

## 三、验证：双向解密

单向自测不够——密钥派生写反了也能让自己的测试通过。所以两个方向都测：

| 方向 | 结果 |
| --- | --- |
| Go 加密 → Rust 解密 | 通过（`go_e2ee_fixture_decrypts_in_rust`） |
| Rust 加密 → Go 解密 | 通过（`rust_e2ee_fixture_decrypts_in_go` 写夹具 + `TestDecryptRustFixture` 解开） |

能双向解开，说明 210000 轮派生、盐/nonce 的字节序、GCM 的 tag 长度与 AAD 处理**逐字节一致**。

### 3.1 Go 侧 3 项单测

往返无损、错口令报「口令不对」、篡改一个字节报同一条、非加密文件与头不完整都能区分、
空口令拒绝、两次加密密文不同（盐与 nonce 随机）、未来版本 2 报「版本 2 不认识」、
轮数取自头部（用轮数 5 构造的密文也能解开，证明解密没把常量写死）。

### 3.2 一处断言纠正

`PK-plain-zip` 只有 13 字节，先被「头不完整」拦下。我最初断言它是 `ErrNotEncrypted`，
与 Rust 不符——Rust 断言的是**错误文本里含「不是 KnowFlick 加密备份」**，两条错误都满足。
改断言而不是改实现：实现没错，是我把两种失败混为一谈了。

## 四、还没做

| 项 | 现状 |
| --- | --- |
| 备份包打包/解包 | 未迁。e2ee 只负责「内容怎么加密」，还没接上 `.kfbackup` 的容器格式 |
| 静态数据库加密 | 明确不做（文档要求独立评估，不以本模块冒充） |
| 口令重置/找回 | 明确不做 |

**Go 版现在能加密与解密，且与 Rust 双向互通，但还没接到备份包的容器上。**
