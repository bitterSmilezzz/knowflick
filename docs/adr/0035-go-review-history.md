# 第二阶段第二十六刀：复习历史账本（review_history）迁到 Go

> 逐次评分的不可变账本（R4/D09）。卡片调度状态仍是当前队列的权威来源，
> 这本账只记录单次动作，不为迁移前凭空补历史。

## 一、迁了什么

| 能力 | Go | 与 Rust 的关系 |
| --- | --- | --- |
| 事件与快照模型 | Event / Snapshot / RestoreCounts | 字段与 JSON 名称逐字对齐 |
| 单条校验 | ValidateEvent | 标准小写 UUID v4、卡片标识长度与控制字符、时间非负、项目标识唯一且严格升序 |
| 整份校验 | Validate | version==1、覆盖起点非负、事件标识不重复 |
| 表结构契约 | validateSchema | PRAGMA table_info 逐列比对名字/类型/非空/主键；默认值不参与比对 |
| 读取 | Capture / Period | 按 reviewed_at、event_id 升序；Period 过滤含两端 |
| 恢复前检查 | ValidateDestination | 内容相同算跳过，同标识不同内容报错 |
| 恢复 | Restore | 插入缺失、覆盖起点取两侧最大值、事务内提交 |

## 二、三条容易做错的语义

### 2.1 项目标识必须严格升序

排序不是装饰：快照要在两侧逐字节可比。Rust 用 windows(2) 逐对比较，
Go 用同样的逐对比较，任何一对不升序都判无效（>= 而不是 >，等于也拒绝）。

### 2.2 恢复时覆盖起点取最大值

合并后的 review_history_started_at = max(本地, 快照)。
用较小值会把已经声称的覆盖范围往回缩——那等于谎称「这段时间我没记录过」。

### 2.3 同标识不同内容直接拒绝

恢复不覆盖本地记录。local == event 才算跳过；否则整轮报错并回滚。
静默覆盖会让用户在不知情的情况下丢失自己的评分历史。
