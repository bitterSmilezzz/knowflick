# 第二阶段第二十刀：自动同步调度与并发保护迁到 Go

> 承接 ADR-0028。同步能跑了，但没人「到点叫它跑」，也没人「防止两轮同时跑」。这一批补这两件。

## 一、迁了什么

| 能力 | Go | 与 Rust 的关系 |
| --- | --- | --- |
| 到期判定 | Due | `interval == 0` 关闭；距上次**尝试**不足 interval 分钟则跳过 |
| 读调度字段 | LoadAccounts | 按 created_at, id 排序，保证行为可复现 |
| 配置解析 | intervalFromConfig | 解析失败按 0 处理 |
| 并发保护 | Lock / TryLock | 等价于 Rust 的 ACCOUNT_LOCK |

## 二、为什么用「尝试时间」而不是「成功时间」

用 `last_attempt_at` 判定到期，而不是 `last_sync_at`。

原因：一个一直失败的账号（密码错了、服务器连不上）如果用成功时间判定，它永远「没成功过」，于是每次轮询都会重试——**不断撞服务器**，还可能触发对方的风控。用尝试时间，失败也要等一个间隔。

这是 Rust 已有的判断，Go 照抄。

## 三、并发保护为什么必须有

一个进程可能持有同一个库目录。两轮同步并发时，两方都会读游标、各自推进、各自提交——后写的一方把先写的进度覆盖掉，用户看到的是「同步跑完了但游标没动」，下次同步又把同一批邮件拉一遍。

`Lock()` 串行化所有邮箱操作；`TryLock()` 给界面的「立即同步」用——拿不到锁说明已经有一轮在跑，不必排队。

### 3.1 锁的测试不靠「读代码觉得对」

`TestLockActuallySerializes` 起 8 个 goroutine，各自进临界区、记录同时在里面的最大数量，断言 `max == 1`。

如果锁写错（比如用了局部变量），这个断言会失败；只读代码看不出这类错误。
