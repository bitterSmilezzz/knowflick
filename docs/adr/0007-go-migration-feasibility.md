# Rust 到 Go：迁移的技术判断（第三部分：可行性评估）

> 承接 [ADR-0005](0005-rust-to-go-migration-rationale.md)（为什么想迁）与 [ADR-0006](0006-go-stack-research.md)（Go 有什么）。
> 这一篇给结论：**能不能迁、迁了值不值、怎么迁**。

## 一、结论

**可以迁，且收益是实测出来的、不是推断。** 但有一个必须先解决的硬问题（ASR），
建议**分阶段迁、先做骨架验证再全量重写**。

| 问题 | 结论 |
| --- | --- |
| 技术上能不能迁 | **能**。Wails v3 提供了 Tauri 的全部关键能力，且类型自动生成 |
| 开发循环能快多少 | **实测快 127 倍**（增量编译 0.069s vs 8.78s） |
| 空间能省多少 | 本机实测：Go 依赖缓存 353 MB vs Rust `target/` 6.4 GB |
| 最大障碍 | **语音转写没有成熟 Go 库**（ADR-0006 §3） |
| 建议 | **分三阶段**，阶段 0 先验证 Wails + SQLite + ASR 三件事 |

## 二、实测数据（本机，2026-11-19，Go 1.27.4 / Rust 现有工程）

这些数字是这一轮**真的装 Go 跑出来的**，不是估算：

| 项 | Rust | Go | 倍数 |
| --- | --- | --- | --- |
| **增量编译**（改一行后端） | **8.78 s** | **0.069 s** | **约 127×** |
| 全量编译（含 SQLite） | 几分钟（720 crate） | **3.66 s**（26 module） | 数十倍 |
| 跑一次测试 | 秒级～十几秒 | **0.425 s** | 明显更快 |
| 依赖缓存/中间产物 | **6.4 GB** | **353 MB** | 约 18× |
| 依赖数量 | **720** crate | **26** module | 约 28× |
| 最小二进制 | 126 MB（调试） | **3.7 MB**（无依赖）/ 9.9 MB（含 SQLite） | — |

**必须说清楚的边界**：

- 这是**最小样例**的对比，不是把整个 KnowFlick 迁完之后的数字。真实项目 Go 侧会大一些。
- Rust 的 8.78 s 是**增量**编译（只改一个文件、依赖都已编好）。如果 `target/` 被清，是全量几分钟。
- Go 的 0.069 s 也是增量。首次拉依赖 + 编译是 7.9 s（含下载）。
- **但即便按最保守的读法**：Go 增量 0.069s 与 Rust 增量 8.78s 的差距是**两个数量级**，
  这个结论不依赖样例大小——因为差距来自「Go 编译快」这个语言特性本身。

### 2.1 为什么差距这么大

不是 Wails 比 Tauri 好，是**编译器设计取向不同**：

- Rust 要做单态化、借用检查、LLVM 优化，720 个 crate 的元数据都要参与。
- Go 的设计目标之一就是**编译速度**：没有泛型单态化（1.18 后的泛型用字典传递）、
  增量编译与缓存做得更彻底、标准库预编译。

这个差距**在日常开发里被反复支付**——每一次「改一行、跑一下」。

## 三、可行性逐项评估

### 3.1 能直接迁的（占大头）

| 现有 Rust 模块 | 行数占比 | Go 方案 | 风险 |
| --- | --- | --- | --- |
| `db.rs` / `store.rs` / `notes.rs` | 大头 | `database/sql` + 纯 Go SQLite | **低** |
| `http.rs` | 中 | `net/http` 或 `resty` | **低**（比 reqwest 简单） |
| `backup_*.rs` | 中 | 标准库 `archive/zip` + `encoding/json` | **低** |
| `media.rs` | 中 | `os` + `path/filepath` | **低** |
| `chunker.rs` / `embed.rs` | 中 | 纯计算，直译 | **低** |
| `mail.rs` / `e2ee.rs` | 中 | 标准库 + 第三方 | **中**（E2EE 要看具体算法） |
| 136 个 `#[tauri::command]` | — | Wails Service 方法 + **自动生成 TS** | **低**（且体验更好） |

### 3.2 有难度的

| 项 | 难度 | 说明 |
| --- | --- | --- |
| **`asr.rs`（whisper）** | **高** | 见 §4，这是唯一可能推翻整个计划的点 |
| `mcp_grants.rs` | 中 | 要看是否依赖 Rust 特有生态 |
| `review_history.rs` | 低 | 数据逻辑 |
| `error_text.rs` | 低 | 字符串映射 |

### 3.3 前端几乎不动

**269 个 TS/TSX 文件、14,553 行前端代码基本不用改**——Wails 跑的是同一套 Web 前端。
要改的只是调用层：`@tauri-apps/api` 的 `invoke(...)` 换成 Wails 生成的绑定。

这是迁移成本里最容易被高估的部分：**前端是资产，不是负债**。

## 四、硬问题：语音转写

这是**唯一可能让整个迁移不成立**的点，必须单独说。

现状：`whisper-rs 0.16` 在 Rust 里是成熟绑定。Go 侧实测（ADR-0006 §3）：
最接近的 `ardanlabs/bucky` 只有 26 star，其余是 0–2 star 的小项目或 Docker 镜像。

### 三条出路与建议

| 方案 | 优点 | 缺点 | 建议 |
| --- | --- | --- | --- |
| **A. 外部进程调用 whisper.cpp** | 编译期依赖彻底消失；ASR 崩溃不影响主进程；升级 whisper 不用重编主程序 | 多一个可执行文件要打包；要管进程生命周期 | **推荐** |
| B. cgo 包 whisper.cpp | 单二进制 | 把 ADR-0005 §2.3 的 `CMAKE_ASM_COMPILER` 问题原样搬过来；cgo 让编译变慢，**抵消迁移收益** | 不推荐 |
| C. 依赖 `ardanlabs/bucky` | 现成绑定 | 26 star，API 稳定性未知；出问题没人兜底 | 谨慎 |

**方案 A 值得展开**：它把「编译期依赖」换成「运行期依赖」，而这恰好是 Go 擅长的事——
`os/exec` 起子进程、stdin/stdout 通信，比 cgo 简单得多。代价是打包时多带一个 whisper 可执行文件，
但那是个**预编译产物**，不参与每次构建。

## 五、建议的迁移路径

**不要一次性重写。** 16,357 行 Rust + 196 个测试，一次做完风险不可控。

### 阶段 0：骨架验证（1–2 天，**必须先做**）

在动手迁任何业务代码之前，先证明三件事能成：

1. **Wails v3 能跑起来**，且能打包出 macOS 应用。
2. **纯 Go SQLite 能读现有的库文件**——这是最实际的兼容性验证（现有 `.db` 直接打开、读出笔记）。
3. **ASR 走方案 A 能跑通**：起一个 whisper.cpp 进程，喂一段音频，拿到文字。

**阶段 0 任何一项失败，就停下来重新评估。** 特别是第 3 项——它单独就能否掉整个计划。

### 阶段 1：并行骨架（数据层先行）

- Go 侧先实现**只读**能力：打开现有库、列出笔记、搜索。
- 前端用 Wails 绑定接上，**与现有 Tauri 版本并存**，通过开关切换。
- 这一阶段不删任何 Rust 代码。

**为什么数据层先行**：它是所有功能的地基，且最容易验证正确性（同一份库，两边读出同样的结果就能对比）。

### 阶段 2：功能对迁（按模块）

按 ADR-0005 的模块清单逐个迁，**每迁一个就删对应的 Rust 代码与测试**：

顺序建议：`db/store/notes` → `media/backup` → `http/mail` → `chunker/embed` → `asr`（最后）。

### 阶段 3：切换与清理

- 前端调用层全部换成 Wails 绑定。
- 删 `src-tauri/`、删 `Cargo.toml`、删 CI 里的 Rust 步骤。
- **这一步之前，Rust 版本必须一直是可用的**——迁移不能让人中途无法工作。

## 六、要付的代价（不打折地说）

1. **16,357 行 Rust 重写**，196 个测试重建。这是几周量级的工作，不是几天。
2. **Wails v3 相对年轻**（v3.1.0，2026-11-01）。踩到框架 bug 时，能搜到的答案比 Tauri 少（star 37k vs 113k）。
3. **ASR 方案 A 引入新架构**：一个子进程要打包、要管生命周期、要处理它崩了的情况。
4. **CI 要重写**：三端打包从 `tauri build` 换成 `wails3 build`，Windows 上那些 cmake 问题可能换成新问题。
5. **过渡期两套并存**：阶段 1–2 期间仓库里同时有 Rust 和 Go，构建时间与心智负担都会上升。

## 七、结论与建议

**建议迁移。** 理由不是「Go 更好」，而是：

1. **开发循环快两个数量级**（实测 127×），这是每天都被支付的税。
2. **空间从 6.4 GB 降到数百 MB 量级**（实测依赖缓存 353 MB）。
3. **跨语言类型自动生成**，消掉 136 处手工对齐——这是架构性的改善，不是换个语言。
4. **前端 14,553 行基本不动**，迁移成本主要在已经明确的后端。

**但必须先做阶段 0。** 特别是 ASR 那一项——如果 whisper.cpp 走外部进程这条路跑不通，
迁移的代价会显著上升，那时候要重新算这笔账。

**不建议**在没有验证 ASR 的情况下直接开始全量重写。
