# ADR-0003：桌面端重构为 AI 个人第二大脑与知识中枢

- 状态：**已接受**（2026-10-18）

## 1. 背景与问题

2026-10-18 实测审计显示：
1. **真实卡库为空**：用户本地 `cards.json` 为 0 条记录，配置了 DeepSeek Key 与 5 个分类，但从未沉淀下真实内容。
2. **根因定位**：纯「Tinder 式左右划卡/冷知识刷题」形态入口过重、回流路径断裂；用户高频的真实信息源（B站视频、小红书、微信公众号、X/推文、GitHub 项目、随手灵感、本地 Office 文档）无法自然进入系统。
3. **性能与规模瓶颈**：原设计基于单个大 `cards.json`，每次划卡全量序列化落盘，且搜索为无索引的每次按键 O(n) 全量遍历，无法承载万级知识库的第二大脑检索与问答。
4. **系统级集成缺失**：缺乏系统托盘、全局快捷键呼出、剪贴板联动与后台常驻能力，无法做到工作流中的随时捕捉。

---

## 2. 核心决策

### 2.1 产品定位与工作流

从单纯的「卡片记忆/刷卡学习」升级为 **AI 个人第二大脑 / 敏捷知识中枢（Local-first PKM & AI Second Brain）**。

核心流转链路：
$$\text{极速多模态收集（Capture）} \longrightarrow \text{结构化提炼与抗臃肿（Synthesize）} \longrightarrow \text{混合检索与温故知新（Retrieve）}$$

- **无 AI 时**：作为高性能、离线、零报错的本地知识库与灵感备忘录，文字记录、文档解析、标签组织、FTS5 全文搜索、导出备份完全可用。
- **配置 AI 后**：无缝解锁语义联想检索、智能归档与切片、周期性认知简报、基于知识库的跨内容深度问答。

### 2.2 界面交互与信息架构

1. **三栏式主工作台**：
   - 左栏：导航、Inbox 收件箱、知识树（分类/标签）、周报洞察、设置、温故入口；
   - 中栏：知识瀑布流与即时过滤；
   - 右栏（可折叠）：正文阅读编辑、AI 对话抽屉与上下文引用。
2. **全局悬浮闪念胶囊（Quick Capture Window）**：
   - 系统托盘常驻，全局快捷键（如 Option/Alt + Space）瞬间在屏幕中央呼出迷你胶囊；
   - 随手打字存灵感、拖入文档解析、贴入 URL 自动嗅探抓取，输入即走，零打断。
3. **温故知新子模块**：
   - 原项目积累的 Tinder 划卡交互、SM-2 与 FSRS 间隔复习算法完整保留；
   - 降级为官方内置的「温故知新」插件，默认关闭，供有备考/概念强化需求的用户一键启用。

### 2.3 底层技术与检索架构

1. **底座选择**：
   - 坚持以 `apps/workbench`（Tauri 2 + React 19 + TypeScript）为唯一核心底座；
   - Android（Kotlin）端保持现状，后续按新数据契约辐射。
2. **存储引擎升级**：
   - 彻底废弃单一单体 `cards.json`；
   - 升级为本地嵌入式 **SQLite 单文件数据库**，支持事务安全、万级条目毫秒级读写、极低内存（数十 MB）；
   - 提供从旧 `cards.json` 的一键无损迁移。
3. **混合检索（Hybrid RAG）**：
   - **全文检索**：SQLite 内建 FTS5，采用中文分词前置策略，配合 `unicode61 remove_diacritics 2`，绕过 trigram 对两字中文的硬限制；
   - **语义检索**：集成 `sqlite-vec` 向量扩展；在个人知识库规模（1 万条以内）采用暴力余弦距离扫描，实测 p99 延迟仅 12ms，避免引入复杂重型的 ANN 索引；
   - **融合排序**：BM25 与向量得分通过 RRF（Reciprocal Rank Fusion）无量纲融合。

### 2.4 三层数据资产模型

数据物理上分为三层，兼顾可回溯性与存储控制：
- **Layer 1: 原始素材（Raw Materials）**：网页全文、剪藏正文、文档文本、图片 OCR 文本与转写文本，按来源独立配置保留策略（默认文字永久、大音视频只留文本与元数据）；
- **Layer 2: 原子知识卡（Atomic Cards）**：AI 或人工提炼的观点卡片，包含规范标签、分类、来源锚点、全局 UUID 与版本时间戳（预留多端同步与合并能力）；
- **Layer 3: 认知产物（Derived Artifacts）**：系统自动聚类生成的周报简报、主题综述、问答记录。

### 2.5 插件化与生态策略

- 采用独立进程沙箱与清单声明权限（网络、文件系统、剪贴板、数据库读写）；
- 实施「插件架构先行，官方插件先跑，第三方生态后开」策略；
- 官方内置插件包含：温故知新（刷卡复习）、高级链接嗅探、文档解析器、本地语音转写、AI 简报；关掉的插件零内存开销；
- 预留 MCP（Model Context Protocol）暴露接口，允许外部 Agent 访问本知识库。

### 2.6 明确排除与架构红线

| 排除项 | 理由 |
|---|---|
| 引入 OpenViking / mem0 外部服务端 | OpenViking 采用 AGPL-3.0 且带非标准限制，阻断闭源商业分发；且其需常驻 Python HTTP 服务，依赖树极重（>3GB），与桌面端轻量目标冲突。采用**自研嵌入式 SQLite 记忆底座**，仅借鉴其 URI 与上下文分层思路。 |
| 本阶段实现云同步与账号服务 | 增加开发周期与运维成本。本阶段保证本地离线绝对可用，数据模型中打齐全局 ID、版本号与墓碑标记，为未来自建服务无缝预留。 |
| 第三方插件市场与开发者签名体系 | M4 之后推进，避免初期分散主线精力。 |
| 富文本高保真版式排版编辑器 | 定位知识卡片与第二大脑，不与 Notion / Word / Typora 竞争排版。 |

## 3. 后果与影响

1. **开发工作区**：开发重心全部集中在 `apps/workbench`（Rust 壳扩展 + React 领域重塑）。
2. **依赖变更**：Rust 侧引入 `rusqlite`、`sqlite-vec`，引入系统托盘与全局快捷键插件；前端重写状态流与三栏工作区。
3. **数据开放性**：用户随时可一键双向导出为标准 Markdown 文件夹（带 YAML frontmatter）或标准 JSON 备份，彻底消除厂商锁定顾虑。
