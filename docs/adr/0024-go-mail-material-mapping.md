# 第二阶段第十五刀：邮件到素材的映射迁到 Go

> 承接 ADR-0023。Go 侧已能解析邮件；这一批把它映射成素材记录，并钉住「同一封邮件只落一行」。

## 一、迁了什么

| 规则 | Go | 与 Rust 的关系 |
| --- | --- | --- |
| 素材身份 | Identity | 优先 Message-ID；没有才退到 `uid:validity:uid` |
| 身份命名空间 | 账号+主机+端口+用户名+文件夹 | 不同邮箱的同一 UID 不是同一封邮件 |
| 素材 id | `mail-<sha256前32位>` | 与 Rust 的 calculate_hash 同构 |
| 无主题 | 「（无主题）」 | 空标题在收件箱里一眼看出没做好 |
| 无正文 | 「（这封邮件没有可读的正文，可能只有附件）」 | 同上，中文占位 |
| 元数据 | Metadata 结构 | 账号、文件夹、UID 三元组、Message-ID、收发件人、日期、附件名、原始大小 |

## 二、为什么身份规则值得单独对拍

素材 id 决定了「重复导入会不会产生副本」。两边算法只要差一点，同一个 Message-ID 就会落成两条素材，用户看到的是「邮件重复了」，而代码里没有任何报错。

所以这条对拍断言的是**最终 id 相同**，不是「两边都有 id」。实测两边都算出 `mail-8a8ab5b0c269c7e2013d06c326e2eb65`。

## 三、验证

| 用例 | 内容 |
| --- | --- |
| Go 7 项 | 同 Message-ID 不同 UID 身份相同；不同 Message-ID 身份不同；无 Message-ID 时按 UID 三元组区分；换文件夹/换主机身份不同；素材 id 稳定且带 `mail-` 前缀；中文占位；元数据往返（含附件名与原始大小）；同一 Message-ID 两次映射 id 相同 |
| 跨运行时对拍 | Rust `go_mail_material_parity` 用同一账号与 Message-ID 独立算出 id，与 Go 的 `mail-8a8ab5b0…` **完全相同**；标题与正文占位也一致 |

## 四、还没做

| 项 | 现状 |
| --- | --- |
| 写库 | **未迁**。素材落库仍走 Rust 的 `db::save_material`；Go 侧只构造出记录 |
| 去重账本写入 | 未迁（`mail_imports` / `mail_rejected` 的插入与清理仍在 Rust） |
| 同步执行与进度 | 未迁 |
| 失败重试与 SyncMode | 未迁（New / History / Retry 三种模式） |
| 真实邮箱邮件 | 未验 |

**Go 版现在能算出一个素材记录，但还不能把它写进库。** 映射规则对齐了，写入链路还没有。

## 五、下一步
