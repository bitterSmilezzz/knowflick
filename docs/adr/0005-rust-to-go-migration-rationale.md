# Rust 到 Go：迁移的技术判断（第一部分：经验教训）

> 这份文档只回答一个问题：**这套 Rust 技术栈在开发过程中到底卡在哪里**。
> 结论先写：迁移的动因是**开发过程的成本**，并非产物体积（产物其实很轻）。
> 第二、三部分（Go 调研、可行性评估）另文，本文不预设它们的结论。

## 一、先把事实摆出来

以下数字都来自本机实测（`apps/workbench`，2026-11-19）：

| 项 | 实测值 | 怎么测的 |
| --- | --- | --- |
| `src-tauri/target/` | **6.4 GB** | `du -sh` |
| 其中 `target/debug/` | **6.4 GB**（几乎全部） | `du -sh target/*` |
| `node_modules/` | 106 MB | `du -sh` |
| Rust 源码 | 21 个文件 / 16,357 行 | `find` + `wc -l` |
| 前端源码 | 269 个文件 / 14,553 行 | 同上 |
| `Cargo.lock` 里的依赖 | **720 个** | `grep -c '^name = '` |
| `#[tauri::command]` | 136 个 | `grep -rn` |
| Rust 测试 | 196 个 | `grep -rn '#\[test\]'` |
| 调试产物 | 123 MB 的 `.app`（内含 126 MB 可执行文件） | `du -sh` |

**一个必须先澄清的事实**：打包后的软件**很轻**。
真正发给用户的安装包只有十几 MB 量级——Rust 的产物优化做得好，这一项不是问题。
占空间的 6.4 GB 全在 `target/debug/`，是**开发期中间产物**。

所以「Rust 占空间大」这句话必须说准确：**不是产物大，是开发过程占地方**。

## 二、真正的问题：开发循环的成本

### 2.1 空间：6.4 GB 的调试产物

`target/debug/` 一个目录 6.4 GB，且**不能随便删**——删了下次 `cargo test` 是全量重编。
仓库里为此专门装了一个周清理任务（`~/.agents/scripts/rust-clean-sweep.sh`，仅当 `target/` ≥ 5 GiB 时清），
这本身就是一条证据：**这套技术栈需要额外的运维手段来控制磁盘**。

对比同一台机器上的 `node_modules/`：106 MB，是调试产物的 **1.6%**。

### 2.2 速度：一次门禁要等十几分钟

`./tools/verify_workbench.sh` 要跑 `npm test` + `tsc` + `cargo test` + 18 套浏览器冒烟。
其中 `cargo test` 在**增量**状态下是秒级到十几秒，但一旦 `target/` 被清理或依赖变动，就是全量重编——
720 个 crate 从零编译，几分钟起步；再加上 `whisper-rs` 这类要现场编 C/C++ 的依赖，时间更长。

这个代价在**每一次**「改一行 Rust、跑一次测试」的循环里重复支付。

### 2.3 测试：跨语言边界的地方最难测

196 个 Rust 测试不算少，但结构上有几处反复踩坑的地方：

- **`renderToStaticMarkup` 测不到 effect**：前端组件用服务端渲染测试时，`useEffect` 根本不跑，
  「存进去的字节能不能原样读回来」这类事**完全没被测到**——这是实测踩过的（附件读回那条路径）。
  修法是把逻辑抽成纯函数（`attachment.ts`），代价是要为「可测」重构结构。
- **真实附件在浏览器里造不出来**：`readNoteMedia` 在浏览器模式返回 null（没有可写的库目录），
  所以「附件插在光标处」「按种类渲染」这些只能靠领域测试守，**没有端到端证据**。
  这是环境限制，不是 Rust 的错，但它说明**跨语言边界的行为很难被自动化验证**。
- **原生依赖的编译环境是外部变量**：`whisper-rs-sys` 要在 CI 的 Windows runner 上现场编 ggml，
  而那条腿**反复因 `CMAKE_ASM_COMPILER` 缺失而红**（第 37、40、42、46、49 轮都遇到，注解签名一模一样）。
  同一份代码重跑就过——这类「环境抖动」消耗了大量排查时间，且**改代码修不了**。

### 2.4 打包：两套工具链、两个产物

这是用户提到的核心痛点，具体是这样：

```
前端 (Vite/TS)  ──build──>  dist/  ──┐
                                      ├──> Tauri 打包 ──> .dmg / .msi / .deb
Rust (cargo)    ──build──>  binary ──┘
```

- **两套包管理器**：`npm` 管前端、`cargo` 管后端，各自有锁文件、各自的更新节奏、各自的安全公告。
- **两次编译**：`tsc`/`vite` 一遍、`cargo` 一遍，互不知道对方在干什么。
- **打包慢**：Tauri 要把前端产物塞进 Rust 二进制再封包，Windows 上还要跑 WiX。
- **不是「单一二进制」的开发体验**：虽然**最终**是一个二进制，但**开发时**要同时盯着两个进程、
  两套日志、两种错误格式。跨语言调用的类型安全靠 `#[tauri::command]` 手写约定（136 处），
  **没有编译器帮你检查前端传的参数对不对**——错了只会在运行时炸。

### 2.5 一个反复出现的模式：边界处必须手工对齐

这 136 个 command 里，每一次改签名都要三处同步：Rust 函数、前端调用、以及可能的类型声明。
漏一处不会编译失败，只会运行时出错。这类「手工对齐」是这套架构的**结构性成本**，不是谁的疏忽。

## 三、这些问题的性质

| 问题 | 是 Rust 的错吗 | 说明 |
| --- | --- | --- |
| 6.4 GB 调试产物 | **是** | 720 个 crate 的调试符号与中间产物，这是编译型语言的固有成本 |
| 全量重编慢 | **是** | 同上；Rust 的优化与单态化让编译更慢 |
| 原生依赖编译环境脆弱 | **部分是** | `whisper-rs` 要现场编 C++，这是「用 Rust 包 C++」的固有复杂度 |
| 两套工具链 | **部分是** | Tauri 的架构选择；任何「前端 + 原生后端」都会这样，但 Go 可以做到**一个 `go build`** |
| 跨语言边界手工对齐 | **部分是** | 换语言能减轻（Wails 自动生成 TS 类型），但不能消除 |
| 测试覆盖不到边界 | **不是** | 这是浏览器/无库环境的限制，换语言同样存在 |

**诚实的结论**：迁移能解决的主要是 **1、2、4** 三项——它们恰好是用户最直接感受到的
「占空间、慢、打包麻烦」。第 6 项换语言也不会好。

## 四、迁移要付的代价（先写在这里，避免只算收益）

1. **16,357 行 Rust 要重写**。这不是「翻译」，是重新实现——`rusqlite` 的 SQL、`reqwest` 的 HTTP、
   `whisper-rs` 的 ASR、`tauri-plugin-*` 的几个能力都要找 Go 对应物。
2. **196 个 Rust 测试要重建**。它们是这套代码的行为契约。
3. **136 个 command 的契约要重新对齐**。前端 269 个文件里的调用点要跟着改。
4. **`whisper-rs` 没有成熟的 Go 等价物**（实测搜索：Go 的 whisper 绑定只有个位数 star 的小项目，
   最近更新在 2024–2025 年，没有一个能直接替代）。语音转写这块要么用 cgo 包 whisper.cpp，
   要么改成外部进程调用——两条路都有新成本。
5. **Go 工具链本机没装**（`go: command not found`），要先解决安装与 CI 配置。
