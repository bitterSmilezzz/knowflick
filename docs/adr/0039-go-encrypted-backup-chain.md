# 第三十刀：加密备份链路（打包 → 加密 → 解密 → 解包）接通并双向互通

> ADR-0036 迁了 e2ee，ADR-0038 迁了容器。这一刀把两者接起来，做出**完整的一条链**，
> 并证明两端都能走通。

## 一、接了什么

| 能力 | Go | 顺序 |
| --- | --- | --- |
| WriteEncrypted | archive.Write → e2ee.Encrypt | 容器在内、密文在外 |
| ReadEncrypted | e2ee.Decrypt → archive.Read | 先解密再读容器 |

先打包后加密：解密方拿到的永远是完整容器，不会出现「解密成功但 ZIP 半截」这种中间态。

## 二、两类失败必须分开

| 失败 | 报什么 |
| --- | --- |
| 口令不对 / 密文被改 | e2ee 的错：「口令不对，或文件在服务端被改动」 |
| 容器不合法（解密成功但没卡片） | archive 的错：「未检测到有效的卡片数据」 |

混成一条会让**「密码错了」看起来像「文件坏了」**——两者的修法完全不同：
前者问用户要口令，后者要重新导出。测试里专门钉了这条：解密成功但容器为空时，
**不能**报成「口令不对」。

## 三、验证：双向完整链路

| 方向 | 结果 |
| --- | --- |
| Go 加密打包 → Rust 解密+读容器（`go_encrypted_archive_reads_in_rust`） | 通过：卡片正文、`theme` 保留、`apiKey` 不在 |
| Rust `zip_store`+加密 → Go 解密+读容器（`rust_encrypted_archive_reads_in_go` + `TestReadRustEncryptedArchiveFixture`） | 通过：卡片逐字一致、密钥未泄漏、**换口令读不开** |

两步都要对才算互通：解密对了但容器读不开、或容器读开了但密钥泄漏，都会被这些断言抓住。

### 3.1 Go 侧 2 项单测

往返（含密文里看不到明文）、口令不对/篡改/容器错/空口令四种失败各自归位。

## 四、一个现状要说清

Rust 侧把 `e2ee_encrypt` / `e2ee_decrypt` 暴露成了 Tauri command，但**前端目前没有任何调用**
（全仓 grep 不到 `e2eeEncrypt`/`e2eeDecrypt`，也没有 `encrypt` 的界面流程）。

也就是说：加密备份在两边都还是**后端能力**，没有界面入口。本轮做的是把 Go 侧的链路补齐并证明互通，
不是「界面能加密备份了」。
