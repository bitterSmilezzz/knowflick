## 一、章程（每批工作都按这几条）

1. **一个批次一个完整增量**：能交付给用户用的一小块，不做「十个来源同时开工」。
2. **证据分级，不混用**：已验收 / 有限可用 / 待真实验收 / 失败；CI 绿只算「自动化通过」，不算产品验收。
   界面文案必须与证据等级一致，不能把「按钮存在」写成「功能可用」。
3. **外部依赖必须真跑**：模型、IMAP、麦克风、安装包首启，没有真实账号/设备就标「待验」，禁止假响应冒充。
4. **数据先于功能**：任何 schema 改动必须带老库迁移路径与老库测试；备份/恢复/删除语义是硬门槛。
5. **不做无证据的承诺**：平台格式没有实测就不写「支持」；来源适配没通过自己的验收购就不展示可用。
6. **一分支一机器、CI 是裁判**：合并前 rebase；PR 上绿了才算过；失败就修，不静音。
7. **文档随代码**：改行为 → 改 README/ADR/验收表；验收表只写有证据的结论。

## 三、P0 交付收口（建议本周内完成）

1. **修 PR #95 的两处红**：Go 单测补 GTK4/WebKitGTK6（本提交）；build 重跑 Robolectric 拉包；必要时把该用例的依赖预下载。
2. **更新 PR 描述**：正文还写着「React + Tauri」，改为「前端 + Go 壳（Wails v3）」，并附发布与验证证据。
3. **合入 main**：PR 通过后 squash/merge（仓库既有习惯是线性历史，优先 rebase 合并）；合入后 main 上
   `workbench.yml` / `workbench-release.yml` 才真正生效，workflow 显示名也会从旧的「Web + Tauri」变成新名。
4. **正式发版**：对 main 的发布提交打注解 tag `workbench-v0.1.0`；确认 Release 附件为
   `KnowFlick-Workbench-0.1.0-macos-arm64.dmg` / `-linux-amd64.deb` / `-windows-x64.exe` + `SHA256SUMS.txt`。
5. **首启冒烟**：
   - macOS：本机挂载 DMG → 拖入 Applications → 打开 → 导入 → 刷卡 → 测验 → 导出；
   - Windows：在现有 Windows 开发机上运行 NSIS 安装器 → 同样五步 → 卸载后无残留配置（除用户库）；
   - Linux：用 CI 产物在 Ubuntu 上装 deb → 同样五步（没有机器就用 VM，结论标「有限可用」）。

**P0 退出标准**：main 绿 + Release 可下载 + macOS/Windows 各有一份首启证据（Linux 至少一份，缺则如实标待验）。
**回滚**：Release 附件可撤；tag 可删；main 上旧版本仍可从历史 Release 取回。

## 四、P1：R0 证据补齐（1–2 周，可与 P2 并行）

按「一项证据一个结论」推进，全部回填到 [FIRST_VERSION_ACCEPTANCE](../FIRST_VERSION_ACCEPTANCE.md)：

1. **真实模型**：任选一个用户已有端点（OpenAI 兼容或本地 Ollama/vLLM），验出卡、问答、引用；
   没有 Key/服务就标「待验」，不再用假响应代替。
2. **真实 IMAP**：先 QQ（授权码 + TLS）与 163；Gmail/Microsoft 若 LOGIN 不适用，标「需 OAuth」。
   记录每个服务商的实际结果，不写「支持邮箱」。
3. **真实麦克风**：macOS 桌面录音 → 保存 → 重启 → 回放 → 导出；同时验系统权限被拒时的中文提示。
4. **Windows/Linux 安装与升级恢复**：安装、首启、升级到同版本、从旧备份恢复；记录平台差异。
5. **磁盘写失败**：用只读/满盘目录构造一次失败路径（专门环境，不在日常机器上做）。

**退出标准**：上面五项都有明确等级与证据链接；没有「未验」却写成「可用」的条目。

## 五、P2：R1 关门（产品层，不阻塞工程）

R1 还差两条门槛：
- 「新手能独立续写并找回」——需要 5–8 人两周的真实试用（或至少 3 人任务式走查 + 记录），自动化替代不了；
- 「完整备份到新目录恢复后一致」——真机跨目录恢复依赖 R3 的库目录切换，R1 不强行做，如实标注。

建议：先用 3 人任务式走查拿到第一轮反馈，再决定是否扩大到 5–8 人；不要等试用才开始 R2。
