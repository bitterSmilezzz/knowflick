# 开发批次、验收与发布

基线：2026-11-12。下面是根据当前缺口整理的实施建议。R0–R5 的范围与退出条件仍以 [产品路线](../DELIVERY_ROADMAP.md) 为准。批次可以并行，顺序由依赖和证据决定；文中没有承诺开发日期、人员分配或发布版本。

## 下一步按什么顺序做

| 工作包 | 从哪里开始 | 交付与验收 | 依赖或外部条件 |

| 6. 高级能力与生态（R5） | 依据真实使用选择一批：高级编辑或属性视图、白板/局部图谱、平板手写、更多连接器、Web、自建分享协作、受控第三方模块 | 每批单独定义性能、开放导出、关闭/卸载、权限、异常与升级行为；插件先验证运行时与官方接缝，再考虑分发市场；Web 分别验收文件、后台、通知、模型与浏览器存储 | 前序本地闭环稳定；iOS/iPadOS、协作模式、连接器清单、插件运行时均需单独决策 |

## 质量门槛和代表性样本

- **数据：**同一测试包至少验证旧版读取、篡改、缺附件、路径越界、空库恢复、非空冲突、幂等重放和取消。笔记、附件、来源、学习状态逐项对账；恢复失败时比对实际已写入条目。删除后同时验证全文、向量、引用、问答及 MCP，不只验证列表消失。
- **检索和回答：**建议的门槛仍是 ≥100 条人工标注中英查询、首 5 条来源命中率 ≥90%，涉及个人资料的关键事实有效引用 ≥95%；越权和编造来源为拒绝发布的缺陷。覆盖短中文、姓名、编号、否定、过期、矛盾和无答案；按来源类型报告。门槛未达到或语料未建立时分别说明。
- **性能：**建议以普通 SSD、8 GB 内存桌面和一款目标 Android 设备建立基线。桌面 1 万篇笔记、10 万切片以及有代表性的媒体量，记录启动可编辑首屏 ≤2 秒、键入 p95 ≤50 毫秒、全文首批结果 p95 ≤300 毫秒的目标与实测。生成、转写和语义检索另报首结果、吞吐和内存；负载时确认还能编辑，任务可取消。目标数值不是现有成绩。
- **体验：**断网且无模型密钥完成记录 → 续写 → 找回 → 引用/导出 → 恢复；已升级的学习用户仍能走原九项闭环。键盘、输入法、读屏、浅深色、窄窗口、Android 分享和触控笔分别测试。建议让 5–8 位首批用户试用两周，观察耗时、失败和放弃点，先取得用户同意再收集诊断。
- **范围和授权：**准备全库、项目 A、项目 B、共享成员、已封存项目和撤销授权的样本，断言越界和失败分支；对 AI 增加错误来源 ID、请求发送前原件变更、随后的撤销和追问；对通知区分“有待处理”“尝试投递”“用户处理完成”。

每次验收登记 `日期｜提交或工作树｜平台与构建配置｜能力编号｜入口与数据｜PASS/FAIL/SKIP｜证据路径｜未覆盖项`。本次推进的 macOS 样本与未完成项见 [验收运行记录](../ACCEPTANCE_RUN.md)，分阶段结论见 R1–R4 进度页。

## Windows 和 Linux 安装验收

1. Windows 使用同一提交构建的 MSI，在独立测试账号安装并首启。Ubuntu 或 Debian 使用同一提交构建的 DEB，在桌面会话中安装并首启。记录系统版本、架构、包名、构建版本和 SHA-256。目标机需本地构建时，在 `apps/workbench` 执行 `npm ci`，再分别执行 `npm run tauri build -- --bundles msi` 或 `npm run tauri build -- --bundles deb`。依赖安装见 [发布工作流](../../../.github/workflows/workbench-release.yml) 和 [Windows 开发机上手](../../WINDOWS_ONBOARDING.md)。
2. 从空库导入实际 Markdown 文档，把素材转为笔记和卡片。用正文短语检索，打开笔记的引用，核对返回的笔记标题和原始素材。刷一张卡并完成一次测验评分，导出卡片和 `.kfbackup`。
3. 重启确认笔记、卡片及学习进度仍在。用独立目标库恢复备份两次，核对条数、跳过数、附件 SHA-256 和来源链接。做升级验收时先从可安装的旧版本创建样本，再升级至候选包并复验。
4. 分别登记系统文件选择器、快捷键、通知、麦克风、包内 MCP 和撤销。涉及系统权限的操作按独立测试账号记录，列明尚缺的设备或凭据。

## 发布准备和未决选择

发布沿用 [多端协作规范](../../MULTI_PLATFORM.md)：GitHub 是双机协作中枢；各端独立版本、按当前端的分支和提交规则推进，合并前以最新 `main` 为基线。发布记录进 `docs/` 与 `CHANGELOG.md`；工作台版本在 `package.json` 和 `tauri.conf.json` 一致后按 `workbench-v*` 走 macOS DMG、Windows MSI、Linux DEB 的各自构建。Android 用独立 `android-v*` 与签名验证，冻结 JVM 宿主仍用 `desktop-v*`。安装包不进 Git；构建出产物只证明打包，真实首启与升级另外验收。

| 待定项 | 何时决定、需要什么证据 |
| --- | --- |
| 首批来源和服务商优先级、目标用户/设备 | R0/R2 开始时先选样本与执行人，用真实接入成功率、失败代价和使用频率定顺序 |
| 编辑器与块文档形式、附件内容寻址和索引拆分 | 先用现有 Markdown 笔记与媒体样本做往返和迁移；定未知块兼容、导出与引用，性能数据支持后再做依赖或数据库选型 |

| Web 生产运行方式、系统签名/分发、平板范围 | 按 R3/R5 和目标平台发布需求分别决策；保留一套桌面/Web 界面，验证宿主差异与设备条件。iOS/iPadOS 不从平板需求自动立项 |
