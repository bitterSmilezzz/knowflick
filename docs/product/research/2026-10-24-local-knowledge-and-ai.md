# 本地知识库、检索、同步与 AI 应用研究

日期与全部网页访问日期：**2026-10-24**。用途：为 KnowFlick 的产品重规划提供架构输入；这是研究与推荐，**不代表这些功能已经实现，也不替代正式 ADR**。

本文只使用产品方、项目维护者或协议维护者的一手资料。标有「事实」的内容来自所链接的官方资料；标有「建议」的内容是针对 KnowFlick 需求的设计判断，需要通过跨端原型与产品验证确认。没有进行性能实测，不能据此承诺笔记数量、延迟或设备配置下限。

## 1. 建议采用的默认方案

**建议：以「原件文件 + 权威业务 SQLite」保存用户资产，以可重建的全文与向量索引提供查找能力，以证据引用连接笔记、知识和应用。** 标品无需账号、无需云服务，未配置 AI 时仍能完成记录、整理、查找、回顾和导出。

具体决策建议：

1. 原始网页快照、附件、图片、音视频、邮件原文等按不可变对象保存；原件不会被摘要或向量替代。
2. SQLite 保存原生笔记正文/结构、来源、版本、组织关系、权限、人工知识整理和学习进度；每个字段明确唯一权威位置，避免文件与数据库同时可写而相互覆盖。
3. 提取文本、OCR、转写、缩略图、分块、全文索引和向量均标记为派生数据，可根据原件与版本重新生成。
4. 首先交付可用的本地全文检索，再增加可选语义检索和 RAG；不用「安装大模型」阻塞记笔记。
5. 知识库是对来源的选择、组织、理解和关系整理，不等同于「已经向量化的文件夹」。一份笔记可以被多个知识库引用，无需复制原件。
6. 精确重复只共享相同字节的对象；语义相似仅提示用户关联或合并，不自动删除。
7. 网盘、自建服务是应用级同步协议的承载，不直接同步正在使用的数据库文件。
8. 本地保存、本机加密、同步端到端加密、本地 AI 和第三方 AI 是五个独立开关与能力，不混用隐私承诺。
9. 个人记忆由可查看、可编辑、可撤销且有来源的条目组成；按个人、工作区、项目限定使用范围。
10. 首批外部 AI 连接使用默认只读的 MCP；Skill 导出是补充交付方式，按宿主做兼容验证。

## 2. 已核验的相关事实

### 2.1 本地优先有成熟先例，但存储模型各异

**事实：** Obsidian 将笔记保存为本地 vault 文件夹中的 Markdown 纯文本文件，并维护可与底层文件发生不一致的缓存。这证明「用户可携带的资产」和「应用索引/缓存」可以分离，不意味着 KnowFlick 必须照搬所有存储细节。[Obsidian：How Obsidian stores data](https://obsidian.md/help/data-storage)

**事实：** Joplin 官方将自身定义为离线优先：各设备保存本地数据，通过上传和下载条目及其变更取得一致；删除也需要传播到其他设备。它的同步机制以驱动抽象对接不同存储服务。[Joplin 同步技术规范](https://joplinapp.org/help/dev/spec/sync/)

**建议：** KnowFlick 原生笔记需要富文本块、手写、媒体、稳定块 ID 和跨端版本关系，因此默认用结构化文档模型与 SQLite 保存原生正文，提供 Markdown/JSON/附件的开放导出；暂不同时承诺「任意外部编辑器直接编辑内部文件、所有富内容无损、多人或多设备同时写」三件事。若后续支持外部 Markdown 文件夹，应当作为有明确冲突规则的文件夹模式。

### 2.2 SQLite 能承担第一阶段检索，但要专门验证中文

**事实：** SQLite FTS5 提供全文检索、BM25 排序、片段与高亮，允许自定义 tokenizer。默认 unicode61 按连续字符类别分词，不是中文语言分词器；trigram 提供子串匹配，但全文查询中少于 3 个 Unicode 字符的子串不会命中。[SQLite FTS5 官方文档](https://www.sqlite.org/fts5.html)

**建议：** 不把「已接 FTS5」等同于中文搜索合格。以真实中文笔记、英文、混合技术名词、两字词、人名、邮箱、项目编号、OCR 错字作为验收集；比较中文预分词、标题/标签精确查找和子串回退的组合。选型前做三端编译与移动端检索测试。

**事实：** sqlite-vec 是可在 SQLite 中存取和查询向量的扩展，官方提供 Rust、Node、Python 等绑定；维护者仍明确标记为 pre-v1，预期存在破坏性变化。[sqlite-vec 官方文档](https://alexgarcia.xyz/sqlite-vec/)、[维护者仓库与稳定性说明](https://github.com/asg017/sqlite-vec)

**建议：** 将 sqlite-vec 放在可替换的检索适配器后面，锁定经过验证的版本，并把向量库当可删除重建的索引。安装包体积、内存、中文召回、Android 绑定和升级兼容未实测前，不把它写成不可变技术承诺。

### 2.3 混合检索和证据定位比单一向量库更接近产品需求

**事实：** Qdrant 官方文档支持结合语义向量与 BM25/稀疏检索，并通过 RRF 等方式融合多个结果集，也支持先召回再重排的多阶段查询。[Qdrant：Hybrid and Multi-Stage Queries](https://qdrant.tech/documentation/search/hybrid-queries/)

**事实：** Claude 的引用 API 可将引用定位到提供的文档内，文本可使用字符区间，PDF 可使用页范围，自定义内容可使用块索引。当前文本引用能力不等于图片中的内容能直接获得精确引用。[Claude：Citations](https://platform.claude.com/docs/en/build-with-claude/citations)

**建议：** KnowFlick 自己保存稳定的证据定位，不依赖某个模型供应商临时返回的文件序号。引文必须能打开当时使用的来源版本；「生成了一条看起来像引用的字符串」不算验证通过。

### 2.4 Qdrant 不只存在服务器部署形态

**事实：** Qdrant 目前提供 Edge，可通过 Python 或 Rust 在本机创建保存于目录中的 shard；官方总览仍标明 Edge 为 beta，API 和功能可能变化。因此不能简单将 Qdrant 描述为只能跑独立服务器。[Qdrant Edge](https://qdrant.tech/documentation/edge/)、[Edge Quickstart](https://qdrant.tech/documentation/edge/edge-quickstart/)

**建议：** 默认架构先评估 SQLite 方案；如果较大资料库、复杂过滤或混合检索压测证明有需要，再评估 Qdrant Edge 或用户自建 Qdrant 服务。增加引擎意味着额外的数据生命周期、索引一致性、备份、升级和多端打包成本；不要仅凭引擎宣传页推定实际性能。

## 3. 「笔记 → 知识库 → 应用」的数据关系

以下均为产品与数据设计建议。

### 3.1 来源与原件

来源记录回答「从哪里来、什么时候来、属于谁、是否获准用于某项 AI 处理」。至少保存：来源类型、原始地址或外部 ID、采集时间、原件对象 ID、可用标题、工作区、内容版本、导入连接器及权限。

原件按内容对象保存。网页正文提取与网页快照分开；邮件展示正文与原始 EML/附件分开；录音与转写、手写轨迹与识别文本分开。没有提取成功时，原件仍能打开、导出和重试处理，界面明确显示待处理或失败原因。

第三方连接不是一次性导入的同义词。记录连接器游标、外部版本与删除语义，并让用户选择「只导入副本」还是「持续连接」。用户在 KnowFlick 删除副本，不应默认删除邮箱或源笔记软件中的原文。

### 3.2 笔记

笔记是可编辑、可检索的用户工作对象，可以来自直接记录，也可以附带一个或多个来源。正文、用户标注和 AI 草稿明确区分。自动摘要、分类或 OCR 不覆盖原文；采纳后产生可追踪的新版本。

稳定文档 ID 与块 ID 是链接、引用、增量索引、冲突处理的基础；移动正文或改标题不应让引用失效。现有卡片、测验、收藏、历史与学习进度作为应用资产继续保留，并可以回指来源。

### 3.3 知识库

知识库保存资料范围、主题组织、已确认结论、标签/实体关系与引用，不将每份原件再复制一套。「加入知识库」默认是建立引用与允许检索的范围；整理成知识条目才是生成一个有独立版本的人工或 AI 辅助成果。

把知识分成三种清晰状态：原始记录、AI 建议、用户确认的知识。AI 生成的关系、分类和结论有撤销入口；同一主题的矛盾证据可以并存，显示时间和来源，避免最后一次摘要抹掉历史。

### 3.4 应用成果

问答、项目摘要、周报、复盘、卡片、测验、文章草稿、营销素材包等都引用知识库中的证据。默认输出到草稿，不自动改变原文、公开发布或回写外部系统。新成果可以再次成为笔记，继续进入整理与应用循环。

## 4. 权威数据、派生数据与任务队列

### 4.1 权威资产

**建议：** 原件对象保存原始字节；业务 SQLite 保存原生正文、对象引用、版本、用户组织、知识整理、学习进度、权限和同步变更日志。这两者共同构成恢复所需的资产，职责互不重叠。

权威存储至少应能回答：一篇笔记当前是什么、过去版本是什么、它引用哪个原件、谁创建/修改、用户允许谁访问。单独备份向量文件不能恢复这些信息。

### 4.2 可重建内容

**建议：** 单独管理提取文本、OCR、ASR、缩略图、分块、全文索引、embedding 与自动候选关系。派生项记录：输入版本、内容哈希、处理器版本、模型/分块配置、生成时间和状态。

「可重建」不等于「可以随意丢弃」：长录音转写和 OCR 重跑可能耗时、耗电或计费，允许备份缓存；但恢复正确性不应依赖某一厂商的向量索引格式。用户修改或确认的转写文本不再只是缓存，应成为有版本的用户资产。

### 4.3 后台任务与一致性

**建议：** 用持久任务队列处理提取、转写、索引与同步，具备重试、取消、并发限制、断点恢复和幂等键。优先顺序是保存原件与正文、反馈已保存、再异步丰富内容。

每份资料的处理状态可见，不因向量化失败让笔记消失。索引更新以文档版本为准；过期任务不能覆盖新版本。默认在外接电源或空闲时做重任务，用户可选「暂停 AI/暂停索引」。搜索可先提供精确结果并提示语义索引仍在更新。

## 5. 检索与 RAG 的默认工作流

以下为推荐的起始工作流，参数须通过评测决定。

1. **先限定范围。** 确定工作区、项目、知识库、时间和允许用于当前 AI 的资料；在召回前进行授权过滤，读取原文和返回结果时再次检查。
2. **识别查询类型。** 项目编号、人名、日期、金额等优先精确字段或全文查找；概念性提问可以追加语义召回。筛选、排序、统计先用结构化查询，避免都交给生成模型。
3. **混合召回。** 标题/标签/正文全文结果与语义结果融合；默认保持引擎可替换，不向产品层暴露数据库术语。
4. **按需重排。** 只有评测证明收益足够时才启用重排模型；避免每次按键都启动多个模型。
5. **组装证据。** 从命中块取相邻上下文，记录来源版本与定位；同一文档的重复片段合并，避免同一观点被重复计算成多条独立证据。
6. **生成并校验。** 回答区分原文事实、跨资料归纳和建议。关键事实带引文；证据不足或互相矛盾时明确说明，不伪造引用或用个人画像补足未知事实。
7. **保存可追踪成果。** 用户采纳的输出保存来源关系和生成信息，后续能看到来源被改动或删除。

**建议：** PDF 至少定位页，文本定位块及字符范围，音视频定位时间段，图片/手写定位原件及区域。OCR/ASR 识别结果只是原件的一种解释，应允许并排校对。引用指向来源版本，不能只存当前文档的字符偏移。

**建议：** 知识图谱在前期用显式链接、标签、主题与可确认的关系表达即可；没有证据证明需要时，不额外引入图数据库。图谱是帮助理解的视图，不是完整知识库的替代物。

## 6. 去重、版本与空间管理

以下均为推荐规则。

### 6.1 精确重复

导入时计算内容哈希和长度，候选命中后验证字节相同，再共享同一 blob。哈希用于定位候选，不能证明两个内容在意义、版权来源或用户意图上相同。两次来源记录、采集时间和上下文仍分别保留。

同一 URL 的页面可以随时间变化；同一封邮件可以带不同附件；相同附件可属于不同项目。不能用 URL、标题、文件名或单独的外部 ID 当作内容去重依据。

### 6.2 近似与语义重复

标准化文本、指纹和向量相似度仅用于提出「可能重复」。提供对照、差异、合并预览和撤销，人工确认后再合并知识条目。保留来源关系与版本，不能让模型因为「看起来差不多」而删掉原件、不同观点或历史变化。

### 6.3 回收与体积

先回收缩略图、过期索引等可重建缓存，再按用户设定管理转写/模型缓存；原件、用户成果和历史版本使用独立保留策略。内容对象仅在无引用且超过回收宽限期后删除。跨设备删除需要墓碑与设备确认策略，避免离线设备重新上传已删除内容。

向量占用必须展示实际字节数。作为容量估算，10 万个 768 维 float32 向量的**原始向量**约 307.2 MB（约 293 MiB），还不含分块文本、索引结构、元数据和数据库开销；不能据此承诺完整资料库只占这么多。分块数、模型维度、原始音视频通常都需要单独控制。

## 7. 同步、自定义存储、加密与备份

### 7.1 自定义服务应是同步驱动

**事实：** Joplin 通过类似文件系统的读、写、删、列举驱动支持 Nextcloud、S3、WebDAV、Dropbox、OneDrive 等目标；服务抽象与本地离线工作可以共存。[Joplin：Synchronisation](https://joplinapp.org/help/apps/sync/)

**建议：** KnowFlick 第一批自定义同步优先考虑 WebDAV 与 S3 兼容存储，以及本地导入/备份目录；第三方网盘按需求和官方 API 可行性逐个接入。「S3 兼容」也需要兼容矩阵，不承诺任意服务都能即插即用。连接器必须报告能力：条件写入、分页、对象大小、重试/限流、删除和断点上传。

**建议：** 每台设备拥有独立数据库，通过带稳定 ID 与版本的对象/变更记录交换数据。先交付笔记级冲突副本和用户比较，再决定是否为同时编辑的块引入 CRDT；CRDT 不能自动解决附件删除、权限、知识结论和外部连接器冲突。

### 7.2 不直接把活数据库放到网盘

**事实：** SQLite WAL 官方明确要求访问同一数据库的进程在同一主机，WAL 不适用于网络文件系统。SQLite 官方亦说明活库外部复制需要正确锁定，并提供 Online Backup API 等生成一致快照的方式。[SQLite WAL](https://www.sqlite.org/wal.html)、[SQLite Online Backup API](https://www.sqlite.org/backup.html)

**建议与推论：** 将正在写入的 `.sqlite`、WAL、向量目录整包交给通用网盘双向同步，不能替代业务同步协议。网盘同步目录与网络文件系统并非同一概念；这里的拒绝依据还包括多设备并发写、分文件上传时序和冲突副本无法合并业务语义。允许上传已完成的一致备份包，但备份包不是可并发编辑的工作库。

### 7.3 五种能力单独说明

**事实：** Joplin 的 E2EE 在同步序列化时加密条目，主密钥由用户密码保护；其设计表明同步密文与设备内可用数据是不同的层次。[Joplin：Encryption 技术规范](https://joplinapp.org/help/dev/spec/e2ee/)

**事实：** SQLCipher 为 SQLite 提供数据库加密，但这项能力的对象是数据库，不能据此推定附件和其他缓存已被加密。[SQLCipher 官方介绍](https://www.zetetic.net/sqlcipher/)

**事实：** Ollama 官方区分本地模型与云模型，并提供关闭其云模型与 web search 的本地模式；llama.cpp 提供在多种硬件上运行本地推理的 C/C++ 实现。[Ollama FAQ](https://docs.ollama.com/faq)、[llama.cpp 官方仓库](https://github.com/ggml-org/llama.cpp)

**建议：** 设置与产品文案分别表达：

- **本地保存：** 默认数据留在设备，离线可读写；不代表设备丢失后别人无法读取。
- **本机静态加密：** 数据库、原件和包含敏感文本的缓存都要覆盖；密钥管理、锁屏行为与恢复策略单独设计。
- **同步端到端加密：** 数据离开设备前加密，存储服务不持有可解密密钥；需要设备加入、密钥恢复、吊销、换钥和冲突测试。
- **本地 AI：** embedding、OCR、转写、重排、生成分别选择本地引擎。只把聊天模型设在本机，不代表其余链路都在本机。
- **第三方 AI：** 明示服务商、将发送的资料范围、用途与费用；本机检索后发送的摘录仍然是数据外发。同步 E2EE 不阻止用户授权的云模型收到明文摘录。

**建议：** 标品默认不配置同步或第三方 AI；用户可以只用基础功能。已下载模型的离线能力与首次模型下载分开说明；联网权限包含更新、模型下载、连接器、网页提取、遥测和插件，不能用某一运行时的 local-only 设置替整个应用作「绝不联网」承诺。

### 7.4 备份必须验证恢复

**建议：** 备份包含一致业务库快照、原件清单与对象、schema 版本、校验清单；加密库需要独立说明恢复密钥。派生索引可选备份。恢复时先校验完整性和版本，再重建索引。测试覆盖全新设备恢复、损坏包、部分附件缺失、旧版本升级和密钥遗失。

同步会传播误删，因此同步不等于备份。保留独立历史快照和离线导出；跨端至少完成一次真实往返恢复验收，才将「资料可带走」列为已交付能力。

## 8. 个人画像应设计成可治理的记忆

### 8.1 竞品事实与启示

**事实：** Claude 官方提供查看、修改、删除记忆及引用过往对话的入口；当前说明亦提醒：删除对话并不自动删除由其生成的独立记忆。项目与账号记忆的实际交叉规则可配置，不能只凭「项目记忆」这个名称推定完全隔离。[Claude：Chat search and memory](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context)

**建议：** KnowFlick 应把这类容易误解的行为做得更显式：删除资料时说明受影响的索引、画像、引用成果、同步副本和备份；不能让「删除笔记」后 AI 仍把旧结论作为当前事实使用而不告知用户。

### 8.2 画像条目的数据与界面

**建议：** 初期把「画像」命名为「我的记忆与偏好」，以可检视条目代替一个不可解释的总评分。每条至少包含：陈述、属于明确事实还是推测、证据与版本、适用工作区/项目、有效时间、用户确认状态、最近更新、排除/遗忘状态。

先做「用户明确确认的偏好、目标、项目背景」；从资料推导的兴趣和习惯先显示为候选。把「最近一个月记录了 6 次某主题」与「你就是某类人」区分开。缺少活动记录不能推断目标未完成；目标进度优先依据用户确认的行动或可靠结构数据。

**建议：** 关键控制必须放在可找到的位置：查看依据、编辑、禁用一条、暂停提取、清空某项目、此笔记不参与画像、当前对话不使用记忆、删除资料同时撤销派生记忆。被用户否认的推断不能在下次索引时无提示复活。

**建议：** 默认不跨项目读取；允许用户有选择地提升某条偏好到个人范围。外部 AI、插件与 MCP 客户端分别授权，不能沿用应用内「可以使用」的权限。敏感主题的自动推断单独选择加入，不把人生建议包装成已经验证的结论。

## 9. 向其他 AI 工具提供知识：MCP 与 Skill 的边界

### 9.1 MCP 默认只读与最小范围

**事实：** MCP tools 用于暴露可发现、可调用的外部能力；协议建议用户可知晓工具暴露与调用并能拒绝操作。2026-07-28 版授权规范针对 HTTP transport；stdio 的凭据机制有所不同。官方安全指南主张从低风险发现/读取权限开始，按需提升作用域。[MCP Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)、[MCP Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)、[MCP Security Best Practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)

**建议：** 第一版仅提供受范围限制的 `search`、`read_source`、`get_project_context` 与 `list_citations`。默认关闭服务，由用户选择项目、知识库和客户端后启用；给每个客户端独立、可吊销的授权，设置结果上限、分页、审计和敏感字段过滤。

只读也可能把信息送进外部模型，所以授权文案要说明读取范围及潜在外发；不默认暴露「读取全部个人画像」或完整资料库扫描。权限必须由服务端检查，不能依靠提示词或工具说明实现。

**建议：** 先验证桌面本机连接；远程 HTTP 和团队协作作为独立里程碑。后续写入能力使用单独 scope 与用户可审阅的草稿/变更，不让通用读权限自动取得删笔记、发邮件或发布内容的能力。

### 9.2 Skill 是工作方法与入口包

**事实：** Agent Skills 规范用 `SKILL.md` 加可选脚本、参考资料和资产描述能力；兼容字段可声明宿主/环境要求，`allowed-tools` 仍为实验字段且不同实现支持可能不同。[Agent Skills Specification](https://agentskills.io/specification)

**建议：** 优先导出便携的项目上下文 Markdown/JSON 与引用清单；可另提供匹配目标宿主的 Skill，说明如何通过已授权 MCP 获取最新资料。静态导出的 Skill/上下文包是有日期的副本，不会自然获得知识库实时同步。

不能声称「导出一次，所有 Agent 自动兼容」。至少列出已验证宿主、版本、所需权限、离线/联网条件和失败回退。Skill 本身也不是隔离或授权边界，不夹带账号令牌、完整私密画像或无必要的可执行脚本。

## 10. 轻量核心与模块化

以下为面向交付的架构建议。

**核心常驻能力：** 保存、基础编辑、附件引用、收件箱/知识库组织、全文查找、历史/回收站、导入导出、权限与后台任务状态。现有卡片/测验闭环保留为应用模块，共用同一来源、搜索与任务服务。

**按需启用模块：** 网页剪藏、邮件连接、第三方笔记导入、录音转写/会议纪要、OCR/手写识别、语义检索、AI 问答、复盘、画像、同步、MCP 与目标宿主 Skill 导出。模块可以延迟加载，模型按需下载，后台资源配额统一管理。

**接口边界：** 连接器产出规范化来源与附件；处理器产出带版本的派生内容；检索器只返回带权限与证据定位的结果；应用模块读取已授权知识并产出成果。不要让每个模块自行建一套笔记库、向量库和账号系统。

第一阶段先实现内部模块与少量官方扩展点，不先做开放插件市场。真正允许第三方代码执行前，必须解决包来源、版本兼容、权限、隔离、更新、卸载与数据访问撤销。把「支持模块化」与「已提供安全的任意第三方插件运行时」分开表述。

## 11. 可替代方案与迁移成本

### 默认：原件对象 + SQLite + FTS5 + 可选 sqlite-vec

**建议适用：** 无服务进程的个人本地库，跨平台桌面优先，后续与 Android 共享数据契约。优点是权威业务与索引边界清楚、基础功能可离线；代价是中文搜索、原件与事务一致性、同步协议及向量扩展升级都需要自行验证。sqlite-vec 目前的稳定性风险要通过可重建索引和适配器吸收。

### 替代 A：Markdown 文件夹为正文权威 + SQLite 索引

**建议适用：** 外部编辑器与用户直接管理文件是核心卖点的模式。代价是稳定块 ID、富文本/手写无损、文件监听、重命名、并发修改与元数据一致性更复杂。可以作为后续文件夹模式，不建议一开始让它与默认数据库正文双向同时为真。

### 替代 B：Qdrant Edge 作为派生索引

**建议适用：** 实测证明其过滤/向量能力带来足够收益的资料库。代价是引入另一套持久目录与生命周期，并承担当前 beta 的接口变化、多端打包及资源控制验证；业务数据继续留在权威 SQLite，可重建导入新索引。[Qdrant Edge 当前状态](https://qdrant.tech/documentation/edge/)

### 替代 C：用户自建检索/同步服务

**建议适用：** 有运维能力、较大资料库或多设备计算分担需求的用户。代价是认证、网络可用性、升级、备份、证书与密钥管理；应为可选配置，不能把本地标品变成必须有服务器才能运行。自托管也不自动意味着 E2EE 或本地 AI。

### AI 引擎：先接用户本机运行时，再考虑内置

**建议：** 第一阶段通过适配器连接用户本机 Ollama/兼容端点，降低随产品分发模型的体积和更新成本；引导页检测连接与模型能力，不要求用户理解 embedding 或端口术语。内置 llama.cpp 可降低外部安装步骤，但带来推理运行时、模型下载、硬件差异、许可证清单与升级测试责任。模型本身的许可须逐个审查，不能从应用 MIT 许可推定所有模型和依赖也可按 MIT 分发。

## 12. 纳入路线前的技术门槛

以下是建议的验收门槛，不是已经达到的结果，也不是未经测量的发布日期承诺。

1. **资产可恢复：** 断电/崩溃后正文和原件关系一致；全新设备能从备份恢复；现有卡片与学习进度迁移不丢失。
2. **基础查找可靠：** 用中英文、人名、两字词、代码编号、时间与 OCR 文本建立固定查询集；统计正确来源能否进入首屏、打开原件是否成功及索引更新延迟。
3. **RAG 可核验：** 有答案、无答案、矛盾、过期、删除、跨工作区越权等查询均有用例；衡量检索命中与引用支持关系，不能只看回答是否流畅。
4. **同步可解释：** 离线编辑、同笔记两端改动、附件中断、重试、删改冲突和设备长期离线有可见结果；所有目标先通过同一组驱动契约测试。
5. **隐私设置真实：** 本地模式的网络行为可观察；云 AI 只收到授权摘录；关闭画像、吊销客户端、删除来源后，后续回答与导出不再使用被撤销内容。
6. **资源受控：** 在用户预期的最低配置测量启动、编辑、滚动、搜索、索引与转写；确认暂停重任务后资源释放。未取得实测前不宣传「海量仍毫秒级」。
7. **可退出：** 导出保留原件、原生文本、来源、知识关系和学习成果；重新导入抽样校验，不能只导出 AI 摘要。

核心路线依赖是：**先保证资产与检索可用，再让 AI 基于证据回答，再增加有治理的记忆、同步和外部 AI 连接。** 邮箱品牌数量、应用模板数量与插件数量不应先于这些基础门槛。
