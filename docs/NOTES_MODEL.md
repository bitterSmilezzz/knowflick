# 笔记数据模型与迁移契约（R1）

日期：2026-10-24。状态：**实施契约**。依据 [ADR-0004](adr/0004-notes-knowledge-applications.md) 与
[产品重规划](product/README.md) 的 R1 首个开发批次：「先写修订与迁移契约，再实现基础编辑和链路」。
本文是代码与测试必须满足的约束；改契约先改这里，再改实现，两边不得漂移。

## 实体与表（SQLite，全部增量添加，不改动既有表）

```sql
notes                一篇可持续编辑的笔记（当前态）
  id                 TEXT PRIMARY KEY           客户端生成 UUID
  title              TEXT NOT NULL DEFAULT ''
  body_md            TEXT NOT NULL DEFAULT ''   当前正文：Markdown 块文档（见「正文格式」）
  notebook           TEXT                       所属笔记本（单层名，NULL=未分组）
  tags_json          TEXT NOT NULL DEFAULT '[]'
  is_pinned          INTEGER NOT NULL DEFAULT 0
  is_favorite        INTEGER NOT NULL DEFAULT 0
  archived_at        INTEGER                    NULL=未归档
  source_material_id TEXT REFERENCES materials(id) ON DELETE SET NULL
  current_revision   INTEGER NOT NULL DEFAULT 1  与 note_revisions 对齐
  created_at / updated_at INTEGER NOT NULL
  is_deleted         INTEGER NOT NULL DEFAULT 0  回收站软删（B02）
  deleted_at         INTEGER
  exclude_from_profile INTEGER NOT NULL DEFAULT 0  不用于个人画像提案；默认关闭排除

note_revisions       修订历史（append-only，不 UPDATE 不 DELETE）
  (note_id, revision) PRIMARY KEY
  title / body_md / saved_at
  revision 从 1 起，单调递增；upsert 成功即追加一行

knowledge_bases      知识库（范围）
  id / name / description / created_at / updated_at

kb_membership        成员关系；同一笔记可属多个库，不复制正文（C01）
  (kb_id, note_id) PRIMARY KEY, added_at

fts_notes            FTS5：title + body；保存同步维护，删除/恢复同步增删
```

既有 `materials` / `cards` / `fts_*` 一律不动：旧卡片 id、FSRS 字段（repetition /
interval_days / ease_factor / stability / difficulty / 评分与复习记录）原样保留；
`cards.material_id` 继续有意义。**新增笔记与旧卡片互不覆盖。**

## 修订语义（防旧草稿覆盖新内容）

`note_upsert` 必须带 `base_revision`：

- 期望修订 = 当前 `current_revision` → 提交：追加修订 N+1，更新当前态，写 FTS，返回新修订号。
- 期望修订 ≠ 当前 → **拒绝**，返回中文错误与当前修订号；调用方不得静默覆盖
  （来自另一窗口、MCP 或同步的旧草稿都走这条防线）。
- 新建笔记 revision=1。
- 修订历史 append-only：恢复回收站、归档、收藏等**元数据变化不产生修订**；
  只有 title / body_md 变化才追加修订。修订号永不回退、不复用。

## 保存顺序与故障

笔记正文存 SQLite（权威），附件仍走 `media/`（R1 切片的新建笔记不带新附件类型，
既有 ink/audio/image 附件通过 `source_material_id` 或正文引用沿用）。
保存在一个事务内完成：修订校验 → 写 notes 当前态 → 追加修订 → 更新 FTS。
任何一步失败整体回滚，不允许出现「当前态已改而修订缺失」或「FTS 与正文不一致」的中间态。

## 正文格式（R1）

`body_md` 是 UTF-8 Markdown 文本：标题外的段落 / 列表 / 待办 / 引用 / 代码块 / 链接 /
行内图片引用（`media/...` 相对路径）。块标识（B01 完整块文档、旁车文件）属于后续批次；
R1 契约只保证：`body_md` 可无损往返（读回==写入），导出 Markdown 即正文本身。

## 置顶与归档（B03）

两个字段一直在契约里（`is_pinned` / `archived_at`），但界面与列表都没用上——
等于字段不存在。现在它们是可操作的：

- **置顶**（`is_pinned`）：置顶的笔记排在同一列表最前，其余仍按更新时间倒序。
  列表条目显示「置顶」徽标；按钮的 `aria-pressed` 与标签（置顶 / 取消置顶）跟着状态走。
- **归档**（`archived_at` 非空）：把笔记从主列表收起来，**不删除、不丢修订**。
  主列表与全文检索默认都不返回它；「已归档（N）」视图单独列出，可逐条「移出归档」回到列表。
- **两件事互不替代**：归档 + 软删（回收站）可以同时成立，回收站视图仍然看得到它；
  归档不会把笔记丢进回收站，回收站也不会替用户归档。
- **都是元数据变化**：不追加修订（与收藏、笔记本、标签同一口径），
  已开着的笔记走同一条保存队列，列表行上的动作用当前修订保存一次。

## 引用体检（C05）

在此之前，引用失效或过期只有**打开那一篇**时才看得到——用户得挨篇点开才知道哪些引用坏了。
`auditReferences` 把全库扫一遍，笔记页顶部出现「引用体检：N 处待复核（失效 a / 过期 b）」，
展开逐条列出「哪篇引用了什么」，点一下跳到引用者。

- 口径与单篇提示一致：目标不在库里 = **失效**；目标正文改过（指纹不一致）= **过期**。
- 回收站里的笔记**不作为引用者**扫描（它自己都搜不到了），但仍可作为**被引用方**——
  引用指向一篇已删笔记正是要提醒的事。已归档的照常扫。
- 素材可以是被引用方（多来源引用），与笔记一视同仁。
- 结果按引用者标题拼音序稳定排序，第二次看还在同一处。
- **就地处理**：每条后面有「删除这条引用」——把这两行（`> 《标题》：片段` 与 `> [回原件](…)`）一起删掉，
  并吸收由此留下的重复空行。打开着的笔记走会话（正常自动保存 + 推进修订），没打开的走 `saveNote`，
  同样产生新修订——**删除是可回退的，旧内容还在修订历史里**。


## 反向链接（B04）

正向引用早就有（正文里的 `> 《标题》：片段` 加一行 `> [回原件](knowflick://note/<id>)`），
但站在**被引用**的那篇上看不到「谁引用了我」。反向链接补的是这一半。

- 判定只看正文里有没有指向本笔记的 `knowflick://note/<id>` 链接（`referencesNote`）；
  只在文字里提到标题或 id 不算引用。
- 回收站里的笔记**不算**引用者（它自己都搜不到了）；**已归档的算**——归档只是收起，
  引用关系还在，藏起来会让用户以为引用丢了，界面上给「（已归档）」标注。
- 自己引用自己不算反向链接。
- 结果按标题拼音序排，来回切换笔记时顺序不跳；每条带引用处的片段（前后各 60 字），
  点一下跳到那篇。

## 笔记模板（B05）

模板只解决「从空白开始写长文太难」这一件事：在「新建笔记」下面那一行选模板，
标题与骨架先摆好，用户接着写。**不自动建笔记**——空笔记堆积是路线图明确要避免的；
模板只在用户点选那一刻起作用，没有定时任务、没有「每天自动开一篇日记」。

- 模板：`blank`（保持老行为）/ `journal` 日记 / `weekly` 周记 / `meeting` 会议 /
  `reading` 阅读 / `project` 项目。每个非空模板都带「## 小节」结构，并至少含一条 `- [ ]`
  待办（待办与正文是同一份数据，见上一节）。
- 变量只有三个：`{{date}}`（YYYY-MM-DD）、`{{weekday}}`（周几）、`{{week}}`（YYYY-Www）。
  **未知变量原样保留**——免得把用户自己写的 `{{…}}` 吃掉。
- 模板内容通过 `session.edit` 进会话，因此照常自动保存、推进修订；不是「先写进界面再假装保存过」。

## 笔记待办（B10）

待办**不是另一套数据**：它就是正文里的 `- [ ]` / `- [x]` 行。正文是唯一真相，
勾选即改那一行，所以待办状态自然跟着自动保存、跟着修订、跟着备份、跟着导出——
不会出现「勾了但正文没变」的两份状态。

- 解析（`parseNoteTodos`）只认行首的待办标记；**代码块里的 `- [ ]` 是示例文本，不算待办**
  （解析时跟着 ``` 围栏走）。`- [ ]` 后面没有文字的不算待办——勾了也不知道要做什么。
- 勾选（`toggleNoteTodo`）只改那一行：缩进与标记格式保持原样，否则正文会产生无意义的 diff
  （修订号照样推进，用户却看不出改了什么）。
- 正文预览里待办渲染成复选框；**只有给了 `onToggleTodo` 的地方才可点**，
  邮件摘要与阅读面板里待办只读——可点的复选框点不动比不可点更糟。
- 正文下方实时显示「待办 done / total 已完成」。

到期提醒与关联项目属于后续批次（B10 余下部分），本轮只做勾选与计数。

## 正文编辑动作（B01）

正文上方一排按钮：标题 / 列表 / 待办 / 引用 / 代码 / 加粗。全部是**纯函数**
（`domain/markdownEdit.ts`）：输入 `{ text, start, end }`，输出新文本与新选区。

- 行内动作（标题、列表、待办、引用）作用于**选中的每一行**：全都有前缀就一起去掉（再点一次即取消），
  否则一律加上；空行不动。
- 包裹动作（代码、加粗）作用于选区：已包住则去掉；**没选中文字时插一对标记并把光标放中间**，
  用户直接开始敲。
- 选区跟着标记走（加前缀往后挪、去掉往前挪），不用手动重选；改完照常走 `onEdit` 自动保存。
- 判定收敛在纯函数里，「多行加前缀」「再点一次去掉」「没选中时插什么」都能被断言。

## 正文编辑：字数与查找替换（B01）

- **字数**按「非空白字符」算（中文没有词边界，按字符数才对得上直觉）；**段落**按空行分块，
  只有空白的行不算段落。显示在正文下方，随输入实时更新。
- **查找**大小写不敏感（英文搜 `note` 命中 `Note`，中文不受影响）；空查询不匹配任何位置——
  空串匹配所有位置毫无意义，还会让「下一个」跳个不停。
- **替换**走与手写完全相同的 `onEdit` 保存路径：自动保存、推进修订、参与冲突判定，
  不另开一条「批量改文件」的旁路。替换 0 次时原文不动（不白写一次保存）。
- 判定收敛在纯函数 `findMatches` / `replaceAllMatches` / `countNoteText`（`domain/noteFind.ts`）：
  匹配位置与替换次数能被断言，而 DOM 里的选区行为不是。
- `Ctrl/Cmd+F` 打开查找栏（在正文里按），`Enter` 下一个、`Shift+Enter` 上一个、`Esc` 关闭。

## 批量移动（B03）

多选手势与「全部知识」列表一致：**Cmd/Ctrl/Shift + 点击**切换选中，普通点击打开笔记并清空选择；
选中后列表顶部出现批量栏（已选 N 篇 / 笔记本输入 / 移动 / 取消）。

- 移动是**元数据变化**：不追加修订（与收藏、置顶、归档、标签同一口径）；已经是目标笔记本的
  笔记不再写一次，`updatedAt` 也不会白改。
- 笔记本名两端的空白会被去掉；**留空 = 移出笔记本**（`notebook` 置空），这是唯一能批量取消分组
  的入口——否则只能一篇篇改。
- 判定收敛在领域函数 `moveNotesToNotebook`（纯函数，两条写入路径共用）：不存在的 id 收进
  `missing` 而不是静默忽略，界面说「N 篇已移动，另有 M 篇没找到」。

## 修订历史（B02）

`note_revisions`（note_id, revision, title, body_md, saved_at）是 append-only 的，
此前只有备份在用——界面既看不到「上一版长什么样」，也没有读的入口。现在有两个只读命令：

- `note_history_list(dir, id)` → `[{revision, title, savedAt, chars}]`，**按修订号倒序**，
  不带正文：正文可能几十万字，列表只需要「第几版、什么时候、多长、什么标题」。
  `chars` 用 SQL 的 `length(body_md)` 算（字符数，不是字节数）。
- `note_history_read(dir, id, revision)` → 该版完整内容；不存在返回 `null`。
  不存在的修订**不是错误**——历史可能被旧版本清过，界面说「读不到了」比报错更准确。

**恢复某一版 = 把那一版的内容再存一次**，走普通 `note_upsert`（base 为当前修订）：
结果是**新增一版**，修订号继续往前走，被覆盖的当前内容仍留在历史里随时能再回来。
刻意不做「改写历史」：那会让 append-only 的前提失效，也会让已发生的冲突判定不可复现。
界面上是两段式（先点「恢复」变成「确认恢复」，再点才落库），因为当前内容会被覆盖。

浏览器体验没有修订表（localStorage 只存当前态），所以 `readNoteHistory` 返回 `null`，
界面如实说「浏览器体验不保存修订历史」，**不显示「暂无历史」**——那是另一句话。
「还没读」与「读不到」也用两个标记分开，否则桌面端在读完之前会短暂显示那句假话。

## 复制与单篇导出（B02）

- **复制**是一次新建：新 `id`、`current_revision = 1`、`created_at/updated_at` 取当前时间。
  保留 `title`（追加「（副本）」后缀，避免列表里两行同名）、`body_md`、`notebook`、`tags`、
  `exclude_from_profile`；**不复制**「属于原来那一篇」的状态：`is_pinned`、`is_favorite`、
  `archived_at`、`is_deleted/deleted_at`，以及 `source_material_id`——保留会让同一份素材被
  两篇笔记声明为「已转笔记」，界面与索引都会给出错误结论。
  复制只产出草稿，落库仍走 `note_upsert`（base=0）：修订号推进与冲突判定只有一处实现。
  返回给界面的是**落库后**的记录，不是草稿——草稿的 `current_revision` 还是 0，
  拿它开编辑器会让下一次保存的 base 与库里的修订对不上。
- **单篇导出**把 `body_md` **原样**写成 `.md`（契约「导出 Markdown 即正文本身」，不补标题、
  不包 front matter，导出文件与库里的正文逐字相同）。文件名取标题并去掉路径分隔与控制字符；
  正文为空时退化为一行 `# 标题`——导出空文件等于丢内容。桌面端用原生保存对话框 +
  `write_text_file`，浏览器体验用下载；取消时界面说「已取消导出」，不假称写入成功。

## 删除与回收站

`note_delete` = 软删（is_deleted=1, deleted_at），FTS 同步移除 → 搜不到；
`note_restore` 恢复并回填 FTS。修订历史在软删期间保留。R1 不做物理清除
（引用计数与墓碑是 R3 的同步前提，见 LOCAL_DATA_AND_AI）。

## 个人画像提案排除

笔记属性 `exclude_from_profile` 默认 `0`。用户开启后，该笔记不进入画像提案选择列表；提案发送前重新读取笔记时也会再次过滤。此标记只控制个人画像提案，不改变搜索、问答或其他 AI 功能范围。旧库升级时为既有笔记补 `0`，备份与恢复保留该属性。

## 知识库

- `kb_create(name)` 名称非空唯一（同名列唯一约束由应用层保证并返回可读错误）。
- `kb_add_note / kb_remove_note` 幂等（重复加入不报错、不重复行）。
- 一个笔记可属多个库；删除笔记后成员关系随软删对检索不可见，物理删除时级联。
- R1 的「搜索命中正文」：`search_notes(query)` 走 fts_notes，可按 kb 过滤（join membership），
  **不同库检索不串库**（过滤在 SQL 层，不在界面层）。

## 导出与恢复（.kfbackup schemaVersion 2）

- 新增 `notes.json`（全部字段 + current_revision）与 `knowledge_bases.json`
  （库 + 成员关系）。manifest.stats 增加 `notes` / `knowledgeBases`，checksums 覆盖两个新文件。
- `schemaVersion: 2`；读取端按「有 notes.json 就恢复」兼容 v1 旧包（无笔记即空集）。
- 恢复到新目录后：笔记正文、修订号、笔记本/标签/收藏、库与成员关系逐项一致；
  既有素材/卡片/附件/学习进度恢复行为不变（回归既有 systemBackup 测试）。
- v1–v5 包不含完整历史，携带当前态与修订号；桌面 v6 包增加 `note_revisions.json`，
  保存数据库中实际存在的历史及其原始保存时间，并收集历史正文所引用的附件。浏览器备份仍不含历史。

### 恢复专用写入（T04，审计 KF-003/KF-006 收口）

恢复是**显式用户动作**，与普通编辑（`note_upsert`）是两个入口：
`note_restore_upsert`（Rust）/ `restoreNoteRaw`（浏览器同语义）按包内当前态**原样**落库。

- **保留项**：修订号（`current_revision`）、`created_at`/`updated_at`、
  `is_deleted`/`deleted_at`（回收站内容不复活、保持不可检索）、收藏/置顶/归档、
  `source_material_id` 与全部属性；成员关系的 `added_at` 保留包内值
  （`kb_restore_membership` 逐条处置）。
- **不伪造历史**：旧包只落一条恢复时的基线修订行（沿用包内修订号）；v6 包按原样恢复
  实际历史，不补造缺失修订。笔记及其历史在一个事务里写入，已有历史不同则拒绝覆盖；
  后续编辑从当前修订继续计数（修订 9 恢复 → 下一笔编辑修订 10）。
- **逐条处置**（`NoteRestoreOutcome`）：`created` / `updated`（包内修订更大，覆盖）
  / `skipped_local_newer`（本地修订更新，不回退） / `skipped_divergent`（同修订号
  内容分歧，保守保留本地等人工处置） / `current`（重复恢复幂等）。
- **知识库映射**：同 id 已存在 → 并入既有库（本地名字保留）；同名异 id →
  并入既有库，成员关系经显式 id 映射迁移；都没有才按包内 id 新建。
  每条失败（库/笔记缺失等）进结构化报告，不吞错假计数。
- 回执按上述处置如实计数；有失败时明确告知「不是完整恢复」并列出明细。

## 迁移

- 不回填：既有 materials 不自动转成 notes（「来源→笔记」映射是 R2 统一笔记模型的事）。
  R1 的新笔记与旧素材在界面共存、都可被搜索。
- 兼容出口：`cards.json`（Android 交换）不动；它不是笔记系统的同步协议。
- **R2 映射（已实现）**：`note_ensure_from_material` 按需把一篇素材映射为可编辑笔记——
  幂等键是 `source_material_id`（重复映射返回同一篇），正文取 `cleaned_markdown ?? raw_text`，
  原素材不删不改（编辑不回写原件），旧卡片与 FSRS 字段不受影响；不做全库启动回填，
  由用户在素材详情显式触发（「转为可编辑笔记」）。
- 升级路径：`init_tables` 增量建表，老库打开即得新表，无数据搬迁、无阻塞。

## 界面契约（链路验收用）

R1 纵向切片必须能在真实界面走通并在冒烟中断言：

1. 新建笔记 → 直接可写（标题 + 正文）；
2. 停止输入后自动保存（无需手动点保存），重启应用后内容在；
3. 加入某知识库；
4. 全文搜索命中**正文**（不是只命中标题）并回到该笔记；
5. 完整导出 → 恢复到新目录 → 正文与库成员关系一致。

无网络、无 AI 密钥时上述链路全部可用。
