# 数据出口清单

这份清单回答一个问题：**这个应用里的数据，会从哪些地方离开本机？**
每一处出口都要说清「带了什么」和「有没有把不该带的带走」。

起因：连续三轮在**不同出口**发现同一类缺陷（服务端错误原文带着 API key 流出去）：

| 轮次 | 出口 | 后果 |
| --- | --- | --- |
| 41 | AI 错误 → **界面** | 截图分享就泄露 |
| 42 | 导出包 → **文件** | 备份包分享就泄露 |
| 43 | Embedding 错误 → **控制台** | 贴日志就泄露 |

修完三处才意识到：**我当时是「发现一处修一处」，没有先把出口列全**。
这份清单就是补那一课。

## 出口逐个对照

| **`.kfbackup` 备份包** | 素材 / 卡片 / 设置 / 产物 / 附件 | ✅ 设置里的密钥字段被 `stripSecrets` 过滤 |

## 已验证的「不该出去的东西」

- **API key**：不进界面错误、不进备份包、不进控制台、不进剪贴板。
  凭据本身存在**库目录之外**：桌面端 `<data_root>/credentials/apiKey.credential`
  （`store/` 的兄弟目录，见 `store::credentials_file`），浏览器体验在
  `sessionStorage`。都不进 SQLite、不进任何导出格式。
  > 注意：正因为它在 `store/` 之外，导出天然带不走它。42 轮修的是**另一条路**——
  > `settings.json` 里遗留的密钥字段会被 `encodeSettings` 原样带走。
- **邮箱密码**：写在 `<库目录>/credentials/mail-<uuid>`，不进 SQLite、
  不进 DTO、不进错误信息、不进任何备份格式（见 [EMAIL_INTEGRATION](EMAIL_INTEGRATION.md)）。
- **带 `user:pass@` 的链接**：手动记录、剪藏两条路径都直接拒（CONTEXT.md 的策略），
  不会把凭据写进来源链接。

## 新增出口时要做的

1. 在这张表里加一行，写清「带了什么」；
2. 如果带的是**服务端返回的原文**，先过 `redactSecrets` / `redact_secrets`；
3. 如果带的是**设置或元数据**，确认里面没有凭据类字段（`stripSecrets` 那条规则）；
4. 加一条**走真实路径**的测试——测工具函数不算（41 轮踩过：只测
   `redactSecrets` 本身，去掉调用点它照样绿）。

## 仍未验证的

- ~~**Windows / Linux 上的出口**~~（2026-10-22 已有证据）：脱敏逻辑在 **Rust 侧**
  （`http::redact_secrets`），三端共用同一份代码与同一套测试；CI 在 Linux /
  Windows / macOS 三台 runner 上各跑一遍 `cargo test`，脱敏用例三端全绿。
  前端那部分（`store.redact`）是 TS，同样三端跑。
  仍未覆盖的是「真实服务商的错误格式」——见下。
- **真实服务商的错误格式**：脱敏规则是按「常见前缀 + Bearer + 长随机串」写的，
  真实服务商五花八门的错误格式里，会不会有规则覆盖不到的凭据形态——
  这个只能靠真实调用暴露（需要 API key）。
