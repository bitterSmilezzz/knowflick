### P2 — 建议

- **`apps/mac/Sources/KnowFlickCore/Models/WebClipEngine.swift:64-72`（`WebClipDigest.attributing(_:)`）** — 去重用的是**精确字符串比对**：`attributed.links.removeAll { $0.url == sourceLink.url }`，而 `sourceLink.url` 取的是 `pageURL`。

  - 为什么是问题：`WebClipDigest` 自己就携带**两个不同的 URL**——`sourceURL`（用户提交的原始地址，例：`https://example.test/article?from=share`）与 `pageURL`（归一化后的规范地址，例：`https://example.test/canonical`）。只有与 `pageURL` **逐字符相等**的链接才会被去掉，于是以下两种输入都会在卡片里留下**两条指向同一页的链接**：① AI 返回的链接带尾斜杠 / 大小写不同 / 带跟踪参数；② AI 直接返回了 `sourceURL` 形态。新加的用例（`WebClipFetcherTests.swift:73-105`）只喂了"与 `pageURL` 完全相等"这一种输入，所以守不住这个边界。
  - 建议：比较前先做一次规范化（去尾斜杠、scheme/host 小写、丢弃已知跟踪参数），或同时按 `sourceURL` 与 `pageURL` 两个形态去重；测试补一条"尾斜杠 / 带 query"的用例。
  - 不确定项：我无法判断上游 AI 实际会返回哪种链接形态（取决于模型输出），上述是按代码可推导的边界，**非实测命中**。

- **`apps/mac/Sources/KnowFlickCore/Models/WebClipEngine.swift:69`（`attributed.source = .imported`）** — 剪藏卡片复用了既有的 `.imported` 来源枚举，但**四个渲染点都把它显示成"导入笔记"**：`CardView.swift:194`（卡片正面 → 「导入笔记」）、`DetailView.swift:160`（详情页 → 「导入笔记」）、`CardExportEngine.swift:161`（导出 → 「📥 个人笔记提纯」）、`CardExportEngine.swift:296`（导出标签 → 「笔记提炼」）、`CardPosterRenderer.swift:134`（海报 → 「导入笔记」）。

  - 为什么是问题：用户刚做的是"从网页剪藏"，卡片翻过来却写着"导入笔记"、导出的海报写着"个人笔记提纯"。本提交既然改了 `CONTEXT.md` 的领域词汇（新增 macOS 入口那一段），却没有为剪藏来源新增语义或调整这几处文案，属于"新功能与既有渲染层的接缝"——不是数据错误，但对用户是明确的口径矛盾。
  - 建议：二选一——① 给 `CardSource` 增 `case webClip`（注意 `CardSource.init(from:)` 对未知 rawValue 兜底 `.seed`，新增 case 不会破坏旧数据解码），并同步四处文案；② 保持 `.imported`，但把这四处文案从"导入笔记"改成覆盖面更广的"外部导入"之类措辞，并让 `CardPosterRenderer` / `CardExportEngine` 不再细分。

## 已核实、不构成问题的点

- **`WebClipEngine.swift:166-198` 的 URL 准入**：只接受纯 `http`/`https`，带 `user:pass@` 的**直接拒**，且对"冒号前像协议、冒号后不像主机"的形态（`javascript:alert(1)`、`tel:12345`）单独识别并报"只支持 http/https"而不是被补成 `https://...`。安全面完整，无 `file://` / 本地路径可乘之机。
- **`WebClipModalView.swift:302-328` 的任务生命周期**：`fetchPage()` 的 `guard !Task.isCancelled, urlText... == submittedText` 失败时**不会**留下 `isFetching == true` 的卡死态——因为唯一能让该 guard 失败而不取消任务的路径（用户改 URL）会先触发 `.onChange(of: urlText)`（`:83`）→ `resetForURLChange()`（`:362-372`），后者显式把 `isFetching` / `isTransforming` 都置回 `false` 并取消两个任务。`transformPage()` 同理。抓取进行中输入框被 `.disabled(isBusy || importMessage != nil)` 锁住，不存在"边抓边改"的竞态。
- **`WebClipModalView.swift:348-352`**：导入走 `store.importCards(selected, insertAtTop:)`（`AppStore.swift:403` 的意图化方法），没有绕过 AppStore 直接改卡片字段，符合 `CONTEXT.md`「对 `seenAt`/`swiped` 的任何写入都必须经由 AppStore 的意图化方法，视图不得直接改字段」。
- **`importMessage` 的计数口径**：`importCards` 返回的 `parsedCards` 就是 `deduplicateAndMerge` 后真正入库的集合（`AppStore.swift:403-415`），所以文案"新增 N 张，跳过重复卡 M 张"与实际一致，不存在"把解析数当新增数"的偏差。
- **正文长度**：`CONTEXT.md` 记录抽取结果"按行截断 4000 字"，因此 `pagePreview` 把 `digest.text` 整段交给单个 `Text` + `fixedSize(vertical:)` 不会构成排版性能悬崖。我原先怀疑这一点，核对 `CONTEXT.md` 后**撤销**。
- **双端对齐**：Android 侧对应逻辑在 `ai/Service.kt:262`（`links = sourceLinks.filter { ... } + links`，把来源链接前置且按 url 精确去重），语义与 Swift 的 `attributing` 一致，`CONTEXT.md` 新增那句"两端提炼后的卡片都把原文链接放在 `links` 首位"成立。（唯一差别是**分层不同**：Android 放在 AI 服务层、Swift 放在 `WebClipDigest` 模型层。行为等价，仅记为观察，不作为问题。）
- **`DeckDeriver.swift:44-52`**：来源开关打开不全时 `.imported` 卡片会被过滤出卡堆——这是 `CONTEXT.md` 已显式记录的口径（"全关则队列为空（含导入卡片）"），且非本窗口引入，剪藏卡与既有的导入笔记卡行为一致。
- **`MacCommands.swift` 的 `⌘⌥I`**：与已有的 `⌘⇧I`（导入笔记）不冲突，也未被系统保留。
